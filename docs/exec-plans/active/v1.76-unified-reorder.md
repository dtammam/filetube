  (common.js) blocks a channel pin from being dropped among book shelves;

  The helper needs a first-class `groupOf(index)` option, not a caller
  hack.
- **F5 - jsdom 29.1.1 (measured):** `PointerEvent` constructor EXISTS;
  `Element.prototype.setPointerCapture` is **undefined**;
  `document.elementFromPoint` is **undefined**; `getBoundingClientRect()`
  returns all-zero rects. Consequences, all of them load-bearing on the
  design: pointer capture must be feature-detected (it would throw in
  tests AND on any engine lacking it), the drop target must be resolved
  from measured row rects rather than `elementFromPoint`, and the helper
  must accept an injectable `measure` hook so a jsdom test can drive the
  REAL handler chain with real geometry. That is what turns "DOM drag is
  untestable-by-necessity" (the standing comment on all five sites) into
  a bound test.
- **F6 - the box that is too small.** `.folder-list-builder`
  (style.css:3010) is `max-height: 240px; overflow-y: auto` and is worn by

- **F7 - why the row "only drags from a small portion".** Every
  `.folder-item-row` is `draggable=true`, but its interior is a text
  input, two checkboxes with `<label>` wrappers, two arrow buttons and a
  remove button. Native drag never starts from a text input (mousedown
  there begins a text selection), so the only live drag zones are the
  handle, the path text and the gaps. Dean's report is precise.

## Design

- **D1 - `wireReorderable(container, opts)`, one helper in common.js.**
  Pointer events only (`pointerdown`/`pointermove`/`pointerup`/
  `pointercancel`), one code path for mouse, touch and pen. Options:
  `rowSelector`, `handleSelector`, `ignoreSelector` (interactive children
  that must never start a drag), `groupOf(index)`, `onReorder(from, to)`,
  `classes` (dragging / before / after - each surface keeps its OWN class
  family so no shipped CSS changes meaning), `scrollContainer`, `measure`,
  `signal`. Returns nothing; re-wiring on rebuild is the caller's job
  exactly as today.
- **D2 - arming, and why touch needs two doors.** Mouse/pen: arm after a
  4px movement threshold, so a click on a sidebar `<a>` still navigates
  and a click on a button still fires. Touch: a 300ms LONG-PRESS arms the
  drag (movement past 10px before that cancels it, so the list still
  scrolls normally under a finger) - this is the only way to honour "the
  entire thing draggable on mobile" without stealing vertical scroll from
  a list that scrolls. The HANDLE is the second door: it carries
  `touch-action: none`, so a touch that starts ON the handle arms
  immediately with no long-press. Once armed, a non-passive `touchmove`
  listener calls `preventDefault()` for the duration, which is what
  actually stops the page scrolling mid-drag.
- **D3 - drop resolution without `elementFromPoint` (F5).** On each move,
  measure every row (`measure(row)`, default `getBoundingClientRect`) and
  pick the row whose band contains the pointer; before/after is the
  half-height rule the shipped `computeDropIndex` contract already
  assumes. Re-measuring per move (not once at drag start) is what keeps
  the indicator correct while the container auto-scrolls under the
  pointer. Row counts here are <= ~30, so this is not a perf concern.
- **D4 - keyboard parity replaces the arrows.** The handle becomes
  `tabindex="0"`, `role="button"`, with an `aria-label` naming the item,
  and ArrowUp/ArrowDown reorder by one slot (Home/End move to the ends).
  After a keyboard move the caller re-renders, so the helper re-focuses
  the handle at the item's NEW index - otherwise every keypress strands
  focus on `<body>` and a second press does nothing (the v1.67 corner-editor
  lesson, verbatim).
- **D5 - click suppression.** A completed drag must not also fire the
  row's click (S1/S2/S4 rows are `<a href>`; a drop would navigate away).
  Suppress the next `click` on the row after any armed drag ends.
- **D6 - per-surface adoption keeps each persist posture (F3).** S3 stays
  deferred-until-Save; S1/S2/S4/S5/S6 stay immediate, each through its own
  existing persist function, with S4's per-source endpoint split and
  failure-reload intact.
- **D7 - CSS.** `.folder-list-builder` gains a `max-height: min(60vh, 520px)`
  scoped to the three FOLDER builders (`#folders-builder-list`,
  `#book-folders-builder-list`, `#music-folders-builder-list`); the one-off
  job list keeps 240px. (Amended after the QA gate, S1: this paragraph
  originally said `#folders-builder-list` alone, while the shipped rule
  covers all three. The three are one visual family and the sizing reads as
  broken if only one grows; ruling 4 kept book/music out of the REORDER work,
  which this does not touch.)
  `.folder-item-row` row gap `--space-5` -> `--space-6`, and its
  interactive children get `ignoreSelector` coverage rather than
  `pointer-events` hacks. Design tokens only - the census
  (`npm run lint:css`) and the ledger must stay green.
- **D8 - what does NOT change.** `moveArrayItem` / `computeDropIndex` /
  `rebuildFullFolderOrder` / every server route / every persist payload
  shape. This wave is a gesture-layer swap, not an ordering-semantics
  change. Any diff in a `lib/` route or a reducer is a defect.

## Named attack surfaces for the adversarial seat

1. **Wrong persisted order.** Drop above/below the first/last row; drop on
   self; drop while the container auto-scrolls. Assert the POSTed array,
   not the DOM.
2. **F4's cross-group drop** - a channel pin dragged onto a book shelf must
   persist NOTHING, and neither module's pins may vanish.
3. **S3's deferred posture** - a drag followed by NO Save must persist
   nothing; a drag followed by Save must persist exactly the dragged order,
   with per-folder name/hidden settings still keyed to the right folder
   (they are keyed by path, so a reorder must not re-key them).
4. **Hidden-from-sidebar folders** (S1/S2) keep their absolute positions
   through `rebuildFullFolderOrder`; the synthetic Downloads folder keeps
   its GET-time splice.
5. **Gesture leaks** - `pointercancel` mid-drag, a second pointer, drag
   ended outside the container, drag on a re-rendered (detached) row,
   listeners surviving an `AbortSignal` teardown, and the click-suppression
   (D5) never swallowing a legitimate click.
6. **Keyboard parity** - focus survives the re-render at the NEW index; the
   arrows are gone, so a keyboard-only user who cannot reorder is a
   CRITICAL, not a nicety.
