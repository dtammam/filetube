# Trash (v1.65.0) - THE DATA WAVE - exec plan

STATUS: DESIGNED 2026-08-01 from Dean's approved rulings
(HANDOFF-features-wave.md wave 2, verbatim - no re-intake). Closes
tech-debt #64 (the 2026-07-30 capture incident: a stray client tap
permanently unlinked 8 files, one non-re-downloadable). FULL gate,
destroy-the-data brief - "I cannot lose data" is the charter.

Dean's rulings, verbatim scope:

1. 30-day retention, configurable in Settings; auto-purge reuses the
   age-sweep machinery.
2. Trash directory PER LIBRARY ROOT -> trashing is an atomic
   same-filesystem rename (no copy, no doubled disk).
3. EVERY delete path routes through trash - including the two-tap
   managed delete that caused the 8-file incident.
4. Restore is FULL-FIDELITY: user-state rows (progress/likes/watched/
   queue - all NINE id-keyed carriers) survive trash and re-link on
   restore. Mechanism: id = md5(path), so the trash move REKEYS the id
   (rekeyMediaState) and restore re-keys it back.
5. A Trash view (restore / purge-now per item).

## Design facts (machine-derived from the surface map, verified at
## main 59f1099)

- EXACTLY TWO code paths unlink library media: DELETE /api/videos/:id
  (server.js ~8649, the only route) and the scan's deferred tombstone
  retry (~3780). Books/music/ytdlp never unlink library media. There
  is NO bulk delete. Both paths reroute to trash this wave.
- The machinery to model on EXISTS: moveItemToFolder (~9437) already
  does rename-first (linkSync + verified-EXDEV-copy fallback), ONE
  re-key mutator over db.metadata/progress/liked/viewCounts/
  deleteTombstones + id-keyed sidecar renames (thumbnail, transcode
  .mp4, background-audio .m4a, narrow-matched subtitles), rollback on
  mutator failure, then post-commit rekeyInFlightState ->
  userStore.rekeyMediaState (all nine carriers, one transaction).
  Trash and restore are that same shape with metadata moving between
  db.metadata and the new db.trash instead of staying put.
- getMediaId = md5(raw stored path string). Roots are never
  realpath'd (FIX-1) - trash paths inherit the same posture.
- THE SCAN HAS NO EXCLUSION PRIMITIVE: every isDirectory() entry
  recurses unconditionally (scanDirRecursive ~4878); no dot-dir skip
  exists anywhere. A trash dir inside a root WILL be re-indexed unless
  all three walkers (media scan + lib/books/scan.js + lib/music/
  scan.js) learn to skip it. This wave adds that primitive.
- Tombstone contract (v1.41.3): tombstones exist ONLY for UNVERIFIED
  unlink conclusions. A successful rename-to-trash is verified and
  mints nothing; the removeAnyway/recoverable-errno paths keep their
  tombstone semantics unchanged (a read-only mount can no more rename
  than unlink).
- The age-sweep pattern to reuse: selectAgedOut (pure selector,
  ~1276) + a sweep wrapper; runs at boot + piggybacked on existing
  work (NO new timer - the scan timer slot is the precedent).
- A new doc namespace requires FIVE co-edits or saves THROW/restores
  drop it: DOC_KV_NAMESPACES (lib/db/sqlite.js), KNOWN_TOP_LEVEL,
  loadDatabase backfill, BACKUP_NAMESPACE_KEYS (~7424),
  validateBackupBundle/importParsedJson classification.
- Pre-existing asymmetry fixed en route: the delete path never
  unlinked the .m4a audio sidecar (move renames it). Trash-as-move
  renames all three id-keyed sidecars; PURGE unlinks all three.
- v1.64's route-alias lesson applied BY CONSTRUCTION: there is NO
  collection-wide DELETE /api/trash. Per-item only: restore is
  POST /api/trash/:id/restore, purge-now is DELETE /api/trash/:id.
  An empty-id form matches no route.

## Mechanism

- TRASH_DIR_NAME = '.filetube-trash' (NOT '.trash' - avoids NAS
  recycle-dir conventions). Location: <matchedRoot>/.filetube-trash/;
  when the root is unattributable, <dirname(file)>/.filetube-trash/
  (same directory -> same filesystem, rename stays atomic).
- Trash-side filename: <trashedAtMs>-<oldId8>-<basename> (flat,
  unique, basename preserved for manual recovery). trashId =
  md5(trashPath).
- db.trash[trashId] = { originalId, originalPath, trashPath,
  trashedAt (epoch ms), rootFolder, item: <the full original metadata
  object> }. The stored item renders the Trash view and restores
  byte-identical metadata (modulo id/filePath/name recompute).
- trashItem(): confine -> link/rename into trash (move's
  link-then-verify pattern; EXDEV -> the existing sha256-verified copy
  fallback, disclosed as the safety net, not the design) -> ONE
  mutator: delete metadata[oldId], write db.trash[trashId], carry
  progress/liked/viewCounts old->trash, retire tombstones both ids,
  rename the three id-keyed sidecars + narrow-matched subtitles ->
  rollback unlinks the trash-side link on mutator failure ->
  post-commit rekeyInFlightState + rekeyMediaState(oldId, trashId).
  ALL NINE carriers ride the existing seam untouched; the queue's
  dead-id read filter HIDES trashed entries and restore makes them
  REAPPEAR - fidelity for free. The bell feed gets the same dead-id
  read filter if it lacks one (verify at t2).
- restoreTrashItem(): originalPath occupied by a NEW file -> 409
  (disclosed; no silent rename). mkdir -p parents (a restore into a
  since-deleted folder re-creates it). Reverse rename + reverse
  mutator + rekeyMediaState(trashId, originalId). The restored id
  equals the pre-trash id (md5 of the same path), so every carrier
  row re-links exactly.
- purgeTrashItem(): the ONLY remaining true unlink for library media.
  Unlink trash file + three sidecars + subtitle sweep in the trash
  dir; delete db.trash record + viewCounts/progress/liked hygiene;
  removeMediaState(trashId). Verified unlink -> no tombstone.
- DELETE /api/videos/:id becomes trash-through: response gains
  {trashed: true}; 409 recoverable-errno, removeAnyway-tombstone and
  ENOENT already-gone branches keep their exact semantics (the
  streams-release + DELETE_PENDING machinery stays for the
  removeAnyway/unlink edge; the happy path is a rename and needs
  neither). The yt-dlp archive append stays at trash time (delete
  intent = don't re-download; still correct after restore or purge).
- Scan deferred retry (tombstone path): renames to trash instead of
  unlinking; failure keeps the tombstone exactly as today.
- Retention: settings.trashRetentionDays, default 30, allowed
  {0 (= keep forever, the cacheMaxAgeDays Off sentinel), 7, 14, 30,
  90}. sweepTrash(now): purge records older than retention; ALSO
  unlink orphan files in trash dirs older than retention with no
  record (crash-window hygiene - link landed, mutator rolled back,
  rollback unlink failed). Runs at boot + on the scan timer slot.
- Trash view: a section on the setup page (Library settings), listing
  trashed items (name, size, trashed date, days left) with per-item
  Restore + two-tap Purge. NO empty-all affordance (per-item only,
  per ruling; smallest destructive surface). GET /api/trash lists.
- Client delete flows: toast copy becomes "Moved to Trash (kept N
  days)"; the hard-delete modal softens its copy to say trash; 409
  read-only toast unchanged.
- Backup: db.trash joins the bundle (all five co-edits). A new bundle
  restored into an OLD build refuses whole (pre-existing validator
  posture, acceptable, disclosed). Bundle carries records, not media
  bytes: a restore onto a different filesystem yields trash records
  whose files are absent - the Trash view shows them; purge tolerates
  ENOENT; disclosed.
