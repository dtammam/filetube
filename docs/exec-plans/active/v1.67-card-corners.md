# Card-corner customization (v1.67.0) - exec plan

STATUS: DESIGNED 2026-08-02. Dean's intake rulings C1-C5 were given in
advance (HANDOFF-card-corners.md, verbatim, do NOT re-intake). This plan
is the reviewers' spec. Dean's request, verbatim:

> You know the icons for like, trash, queue, download? There are four
> corners. I want to make the menu give an option for which to pick for
> the top left, top right and bottom left (bottom right obstructs time
> we shouldn't use it) let one pick which to set for each corner (or
> none for them). And add share, reheat as options with the glyphs
> there as well.

Rulings (compressed; the handoff holds the verbatim text):

- **C1** per-user SERVER-persisted (Dean overrode device-local).
- **C2** no duplicate control in two corners - the picker drops chosen
  controls from the other corners' options.
- **C3** the card TILES only, wherever they render; music ROWS and book
  ROWS untouched.
- **C4** an inapplicable control renders NOTHING in that corner, never a
  fallback control.
- **C5** defaults keep today's layout: TL Download, TR Delete, BL Like.
  Queue becomes assignable (and is therefore ABSENT by default - this is
  the deliberate fix for the duration-badge collision, disclosed).
- Queue glyph promoted to a real `icon-queue` mask: approved.

## Design decisions

- **D1 - storage.** Three mirrored keys `cornerTL`, `cornerTR`,
  `cornerBL`, each one of
  `download | delete | like | queue | share | reheat | none`. All values
  match the existing shape validator, so they join
  `MIRRORED_SETTING_KEYS` with no new table, no schema bump (stays v7),
  free backup coverage. Semantics: ABSENT key -> that corner's C5
  default; explicit `none` -> empty corner; garbage value -> the C5
  default for that corner (the `starRatings` garbage-tolerance
  precedent: readers defend, the lane stays shape-only). `null` clears
  back to default (existing lane semantics).
- **D2 - authority + render timing.** Server-authoritative per C1.
  Deliberately NO localStorage lane: a device-shared cache of per-user
  prefs is the v1.53 cross-user-bleed class (clears on login AND
  logout), and the mirror lane's device-wins seeding semantics are the
  OPPOSITE of C1. Instead main.js's `loadLibrary` fetches
  `/api/auth/me` IN PARALLEL with the existing `/api/config` await and
  latches the corner prefs per view instance before the first card
  render (the skeleton grid already covers the wait; no
  paint-then-shuffle). Fetch failure or signed-out shell -> C5
  defaults.
- **D3 - one renderer, position split from identity.** A module-scope
  pure function `buildCardCornerButtonsHtml(item, prefs, caps)` returns
  the markup for the three assignable corners; exported via the
  existing `module.exports` guard (the
  `buildBookRowCardHtml` precedent); `buildCardHtml` calls it with the
  view's latched prefs. New positional classes `.card-corner-tl`,
  `.card-corner-tr`, `.card-corner-bl` carry the anchor geometry
  (token-exempt positional comments, same style as today's rules); the
  control classes (`.card-delete-btn` etc.) KEEP look/behavior and
  SHED their positional declarations. New `.card-share-btn` and
  `.card-reheat-btn` mirror the sibling overlay look (scrim, radius,
  opacity 0.85 resting). Never a second copy of the renderer (v1.41.4).
- **D4 - applicability (C4).** download/delete/like/queue apply to
  every card item. share applies iff the item has a server-derived
  original link: `/api/videos` list projection ADDS `watchUrl` (same
  derivation as the single-item route; the never-approximate-a-
  server-resolved-field lesson, v1.52) and the renderer gates on it.
  reheat applies iff the module capability says enabled: when any
  latched corner pref is `reheat`, `loadLibrary` resolves the shared
  capability probe (common.js) before first render; disabled or
  unknown -> that corner renders NOTHING. Inapplicable = empty corner,
  never a substitute (C4).
- **D5 - duplicate defense at the renderer.** C2 is editor-enforced,
  but a direct `POST /api/me/settings` can set the same control in two
  corners. The renderer dedupes: corner order TL > TR > BL, a control
  already rendered this card renders nothing in a later corner. Tested.
- **D6 - share action = one shared decision helper.** Extract the
  navigator.share-vs-clipboard decision from watch.js into a common.js
  helper `shareExternalUrl(url)` returning the outcome
  (`shared | copied | unavailable`); watch.js keeps its own button
  label/reset UI but calls the helper (one decision function,
  v1.41.7); the card handler calls the same helper with lightweight
  card feedback. `test/integration/watch-share-button.test.js` must
  stay green unmodified (behavioral lock on the refactor).
- **D7 - reheat action on a card.** Same POST as the watch page's
  per-item reheat, with lightweight button feedback (busy -> done or
  error, self-clearing). The watch page's relocation-offer modal stays
  a watch-page affordance - NOT offered from cards (disclosed in
  ROADMAP; the reheat itself is identical server-side). 409
  already-running and 404 ineligible surface as the error state, not
  silence.
- **D8 - icon-queue promotion.** New `public/assets/icons/queue.svg`
  using the exact path from today's inline card svg (visual identity
  preserved), `.icon-queue` mask rule + membership in the `@supports`
  currentColor group, base mask only (heart/share/flame precedent,
  absent from the emoji block). `buildCardHtml`'s inline `<svg>` is
  replaced by `<i class="icon-queue"></i>`. Machine-enumerate other
  inline copies of that path at implementation (predicted: the card
  builder is the only one).
- **D9 - the editor.** Three labeled pickers (Top left / Top right /
  Bottom left) in the Appearance box, rendered by setup.js modeled on
  `renderBottomBarEditor`: each select lists the six controls plus
  None, MINUS controls chosen in the other two corners (C2); seeds
  from `GET /api/auth/me`; writes the changed key via
  `POST /api/me/settings` on change; no localStorage (C1). Reheat and
  share appear as options unconditionally (applicability is per-card
  at render time, C4 - the editor is not the applicability gate).

## Gate brief - named attack surfaces (adversarial seat first, then QA,
## sequentially, never both on the tree)

1. **Settings injection past the editor.** Direct POST of duplicate
   controls (D5), garbage values, `none` everywhere, 32-char boundary,
   key clearing; prove the renderer never interpolates a pref string
   into markup unchecked (XSS via settings value).
2. **The delete arm machine after relocation.** Two-tap + confirm copy
   + ~3s auto-disarm + cross-button disarm in EVERY corner, driven by
   real clicks on the P9 harness; prove the trash semantics (v1.65)
   unchanged.
3. **Decision vs use (the v1.66 lesson, struck 3x).** Mutate the
   renderer call INSIDE buildCardHtml (drop the prefs argument, pass
   defaults) - a surviving mutant means the full-chain suite is bound
   to the reducer, not the render.
4. **C4 emptiness.** An inapplicable corner must contain NOTHING - no
   empty button, no fallback control, no layout ghost.
5. **Multi-user bleed.** Two users, one device: prove no corner pref
   leaks across login/logout (there must be NO localStorage lane).
6. **Regression sweep of the shed positional rules.** Every existing
   surface that renders the control classes (cards only, per P1 - but
   PROVE it: a stray `.card-like-btn` consumer positioned by the old
   rule would silently lose its anchor).
7. **Backup/restore.** Corner prefs survive a backup/restore cycle via
   settingsJson (existing lane - prove, don't assume).

## Residuals accepted in advance (disclosed, tracked if they survive)

- Card reheat offers no relocation-offer modal (watch-page affordance).
- The editor is the only C2 enforcement point server-side writes can
  bypass; the renderer's D5 dedupe is the defense.
- Reheat's applicability is module-level (matches the watch page), so
  a non-yt-dlp item with a reheat corner shows the button and surfaces
  the server's honest 404 as an error state on click. This matches
  today's watch-page semantics exactly; per-item eligibility gating is
  deliberately NOT invented here.
