# v1.97.0 — "Hide from feed" (per-user, manual, reversible)

Status: ACTIVE. Branch `release/v1.97.0`. Wave B of the two-wave mobile batch
(Wave A = v1.96.0 watch action bar, shipped).

## Problem (Dean)

A manual, NON-algorithmic per-user prune for the MODERN YouTube feed. Tapping
"Hide from feed" removes a video from THIS user's modern feed only — it does NOT
delete, and the item stays fully findable via search, channel, playlist, folder,
the classic/feed home views, and Liked. Daily-consumption pruning, not filtering/
sorting/recommendation.

## Hard constraint (B1)

The new set is DELIBERATELY SEPARATE from the admin/global `hidden` RBAC
visibility flag (v1.79-1.81 — `metadata.hidden` / folder `hidden` /
user_restrictions). Different name (`feedHidden` / `user_feed_hidden`), different
mechanism, different table. It must NEVER become a permission/visibility control
or a leak surface: hiding an item from your feed does not restrict it for anyone,
and a restricted item's visibility is unaffected by feed-hiding.

## Model (B1) — mirrors user_liked EXACTLY

- **Schema v16 → v17** (append-only migration, the v11 lesson). New table in
  lib/db/sqlite.js `if (current < 17)`:
  ```
  user_feed_hidden (
    user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    media_id TEXT NOT NULL,
    hidden_at TEXT,
    PRIMARY KEY (user_id, media_id)
  )
  ```
- **lib/auth/store.js** prepared stmts mirroring user_liked: `addFeedHidden`
  (INSERT ... ON CONFLICT DO NOTHING), `removeFeedHidden`, `getFeedHidden`
  (SELECT media_id ... ORDER BY hidden_at DESC, media_id), `delFeedHiddenByMedia`
  (cascade), `rekeyFeedHidden` (UPDATE OR REPLACE, move). Store API:
  `getFeedHidden(userId)`, `addFeedHidden(userId, id, at)`,
  `removeFeedHidden(userId, id)`.
- **Lifecycle wiring** — the id-keyed-carrier discipline (the recurring class):
  - `removeMediaState()` (store.js ~549): add `s.delFeedHiddenByMedia.run(id)`
    beside `delLikedByMedia` — a purged video sheds every user's feed-hidden row.
  - `rekeyMediaState()` (store.js ~578): add `s.rekeyFeedHidden.run(newId, oldId)`
    beside `rekeyLiked` — a moved video carries the flag to its new id.
  - (These are the SAME two sites user_liked uses. No new call sites — feed-hidden
    is a disk-independent per-user membership, exactly like liked.)
- **Backup namespace:** user_* tables are NOT in db.json BACKUP_NAMESPACE_KEYS
  (they live in SQLite, exported via the sqlite backup path like user_liked).
  Confirm feed-hidden rides the same SQLite export as user_liked (no new work if
  the whole DB file is the backup unit; verify).

## Read filter (B2) — MODERN grid ONLY

In server.js `GET /api/home`, INSIDE `if (req.query.view === 'grid')` (~9724):
- gather `const feedHiddenSet = new Set(userStore.getFeedHidden(userId));` beside
  the other per-user reads (~9698).
- skip in the grid MEDIA loop AND the grid podcast loop, BEFORE `cand.push`, so
  pagination `{items,total,offset,limit}` stays correct (filter before the slice
  at ~9793-9796): `if (feedHiddenSet.has(id)) continue;`.
- Applies to any modern-feed card by id (media + downloaded podcasts) — per-ITEM,
  which is per-video in spirit (B5); NOT per-channel.

Do NOT touch (they stay COMPLETE): the row `records` path (the "feed" home view,
~9800), /api/videos, library/folder/channel/playlist/search, music, Liked, the
You-tab's OTHER sections. Only the modern grid honors feedHidden (Dean's call).

## Routes — mirror /api/liked

- `POST   /api/feed-hidden/:id` — add. Existence-gated + `restrictedVideoMutation`
  guard (no restricted-id oracle/persist, the /api/liked posture). → `{hidden:true}`.
- `DELETE /api/feed-hidden/:id` — idempotent remove (no existence gate). → `{hidden:false}`.
- `GET    /api/feed-hidden` — the You-tab restore list. Returns the user's
  feed-hidden items, RBAC-filtered (`mediaVisibleTo`) so a since-restricted item's
  title/id never leaks (the inverse of the v1.80 list-leak class), newest-first.
- CLASSIFY both mutating routes `personal` in
  test/integration/route-write-classification.test.js (v1.81: gating one route
  misses its plural). NOT capability-gated — the user's own state, like liked.

## UI (B3) — corner affordance on modern-feed cards

The 3 configurable card corners (v1.67) are all occupied by default and are
GLOBAL across grids; feed-hiding is feed-specific. So a dedicated feed-only corner
affordance (Dean pre-approved "a small corner menu"). Exact shape pending the UI
recon; keep it a corner affordance, on the modern feed only, per-VIDEO. Clicking:
optimistic removal of the card + `POST /api/feed-hidden/:id`.

## Reversible (B4)

- An UNDO toast the instant you hide (reuse showToast's undo action) → `DELETE
  /api/feed-hidden/:id` + restore the card (or a light re-fetch).
- A "You"-tab "Hidden from feed" section listing pruned items with a Restore
  control (GET /api/feed-hidden). No one-way trap.

## Scope discipline (B5)

Per-VIDEO only. "Hide everything from this channel" is a separate future feature;
NOT built here.

## Tests (predictions the suite re-verifies)

- Schema: v17 migration creates user_feed_hidden; is append-only + re-runnable;
  existing rows survive an upgrade.
- Store: add/remove/get round-trip; cascade drops the row on media removal; rekey
  carries it on move (mirror the user_liked lifecycle tests).
- Route classification: both new mutating routes are classified `personal`; the
  forcing net still passes (no unclassified route).
- **Bidirectional (the crux, both the v1.80 leak class AND its inverse):**
  - the modern grid EXCLUDES a feed-hidden id, and pagination total/offset stay
    correct (hide N, total drops by N, no gaps).
  - EVERY OTHER surface STILL returns it: /api/videos, the row home feed, search,
    folder, channel, playlist, Liked, music. (A feed-hidden item is fully findable.)
  - feedHidden NEVER conflates with admin `hidden`: feed-hiding does not set/read
    `metadata.hidden` or any restriction; a restricted item and a feed-hidden item
    are independent; GET /api/feed-hidden does not leak a since-restricted title.
- FULL `npm test` after the per-user-state + route changes (the pre-commit hook is
  UNIT-ONLY and can hide a red integration suite).

## Adversarial attack surfaces (brief)

- Prove feed-hide LEAKS into another surface (a hidden item vanishes from search/
  channel/playlist/folder/liked/row-feed, or its count/title drops from an
  aggregate) — the v1.80 list-leak class, inverted.
- Prove it gets CONFUSED with admin `hidden` (feed-hiding restricts an item for
  others, or an admin-hidden item's feedHidden state affects RBAC).
- Prove it breaks modern-feed PAGINATION (total/offset/limit off by the hidden
  count; gaps or dupes across appended pages; the seeded-random path).
- Prove a purge/move drops or mis-carries the flag (cascade/rekey), or that a
  restricted-id POST is an existence oracle.
