# v1.404.0 - picture-in-picture works on the iPhone: the app (native) and Safari

Kickoff 2026-11-05 (FileTube Root, Opus). **Builder: Smart (Opus).** Why the tier: a new bridge capability, intent
and event across two apps (the web ships first and stays inert until an app build announces the capability, the
v1.399.0 / v1.401.0 pattern), plus an open diagnosis on Safari the build must measure and decide. Not Extreme: no
compositor frame-ordering (PiP is Apple's own window), no data. The iOS half is the iOS Root's (Dean's Mac, the relay
below).

## Why

Dean, 2026-11-05: "The picture-in-picture mode never worked in iOS. Like, it just, the button doesn't work. It works in
the browser in desktop ... it never worked on iOS."

**Root cause in the app (Root, 2026-11-05, read from source on main 69bbe90f, unchanged at ebf94bd3):** the button (`#pip-btn`, a
`#settings-menu` row; wired in player.js ~8854) calls the STANDARD `mediaPlayer.requestPictureInPicture()` and swallows
any rejection (`pr.catch(function () {})`, LESSONS-rules "a feature absent with no console error = a swallowed
rejection"). Since v1.399.0 (`nativeVideo`) the app's picture is a native AVPlayer layer and the web `<video>` has NO
`src` (native-bridge.md section 3: "its own media element is silenced"), so WebKit rejects the request (an element with
nothing loaded) and nothing happens. Before v1.399.0 the home-screen PWA / app ran the same silent path. No
capability, intent or event for PiP exists in the bridge today (native-bridge.md sections 1-3, host-adapter.js
`CAPABILITIES` line 14). So in the app PiP can only be native: `AVPictureInPictureController` on the native player
layer, started by the web button over the bridge.

**Safari: not yet root-caused.** The same standard call runs on a real, playing `<video>` there; the silent catch hides
why it fails. W3 measures it.

## Rulings (Dean, 2026-11-05)

- **Q1 - the button starts and stops picture-in-picture on the iPhone**, in the app and in Safari. Never a dead button:
  where PiP cannot work, the button is hidden (the v1.22.0 AC58 rule, kept).
- **Q2 - automatic PiP in the app:** a PLAYING video goes into picture-in-picture by itself when you leave the app
  (swipe home, switch apps). A paused video does not. The button still works.
- **Q3 - Safari too:** fix the web button to use Safari's own PiP; if Safari refuses, hide it - never a silent no-op.
  Automatic PiP in Safari only if WebKit offers a web API for it (read the source; do not invent one); otherwise Safari
  is button-only, stated plainly in the release notes.
- **Q4 - everything else stays:** the dock (v1.401.0), the minimize pull, full screen, captions, chapters, desktop PiP
  (byte-identical), music and podcasts (no PiP for audio, as today's `.audio-mode` CSS).

## Contract (add-only; frozen by this plan, confirmed by the iOS Root through Dean before the web merges)

- New capability **`nativeVideoPip`**, announced only beside `nativeVideo`. CAPABILITIES in host-adapter.js,
  native-bridge.md and the schema gain it (add-only).
- New intent **`video.pip`** `{ action: 'start' | 'stop' }` (web to native), sent only under the capability and only
  while native owns the current video. Native: `start` begins `AVPictureInPictureController` on the native player's
  layer (a user-initiated start; the web sends it from the button's click); `stop` ends it. A `start` while already
  in PiP, or a `stop` while not, is a no-op.
- New event **`videoPip`** `{ active: boolean }` (native to web): on every PiP start and stop, whoever started it (the
  button, automatic PiP, Apple's own PiP controls), and once in answer to the capability being announced (`false`).
- **Automatic PiP (Q2):** native sets `canStartPictureInPictureAutomaticallyFromInline = true` while its owned video
  is PLAYING and `false` while paused, ended or idle. It holds while the surface is docked or hidden (`visible: false`):
  a video that is playing in the mini player also floats when you leave the app.
- PiP's own controls (play / pause, skip) act on native's player; the web learns the state through the existing
  audio/video state events, unchanged. PiP's "return to app" button ends PiP and the picture returns to its surface
  (the web's last `video.surface`).
- PiP survives in-app (SPA) navigation and the dock. On a main-frame navigation commit native ends PiP with the rest
  of the held capabilities (section 6), and on `audio.stop` / a new video. (Builder, W1: the kickoff said `video.stop`; the bridge has no such message, `audio.stop` is what stops native. A correction, not a contract change.)

## Web requirements

- **R1 - the app path.** With `nativeVideo` + `nativeVideoPip` and a native-owned video: the button posts
  `video.pip start` / `stop` (pressed state from `videoPip`), never the standard API. `videoPip { active: true }`
  counts as a native presentation everywhere today's PiP signal does (`inNativeFullscreen`, the minimize chevron,
  watch.js's note) - one predicate, not a second copy. While PiP is active the player box shows the thumbnail with a
  "Playing in picture-in-picture" label (the surface posts `visible: false`, then `visible: true` again on
  `active: false`).
- **R2 - no dead button in the app.** `nativeVideo` WITHOUT `nativeVideoPip` (app v0.16 / v0.17 builds): the button is
  hidden. A web-element video in the app that native does not own (the Feed, previews, 360): the standard path (R3)
  if WebKit allows it there, else hidden.
- **R3 - Safari (and desktop browsers).** Diagnose first: replace the silent catch with a toast carrying the error's
  `name` (e.g. "Picture-in-picture is not available here (NotAllowedError)"), and read WebKit's source for every
  reject path of `requestPictureInPicture` and `webkitSetPresentationMode` (the user-gesture rule, readyState, the
  `disablePictureInPicture` / presentation-mode support checks). Use `webkitSetPresentationMode('picture-in-picture')`
  where `webkitSupportsPresentationMode('picture-in-picture')` is true (iOS WebKit's long-standing path), else the
  standard API; exit symmetrically. Check that a tap on the `#settings-menu` row really produces a `click` on iOS (the
  player's touch handlers `preventDefault` on parts of the surface; v1.34.1 notes iOS synthesizes no click there) and
  that nothing async runs before the call (the gesture must still be live). Desktop: byte-identical behaviour.
- **R4 - the PiP state is honest.** `enterpictureinpicture` / `leavepictureinpicture` / `webkitpresentationmodechanged`
  (web) and `videoPip` (native) drive the button's pressed state and label (Picture-in-picture / Exit
  picture-in-picture). Faux fullscreen, the rotate-to-fullscreen bounce (player.js `webkitbeginfullscreen` handler) and
  the minimize pull must never kick a video OUT of PiP.

## Evidence

**Design note (R1, attack surface 4).** Native's state answers on the proxied element as `webkitPresentationMode` (native-audio.js `attach`, the v1.397.0 proxy
pattern) and `pipSet` fires `webkitpresentationmodechanged`. So `inNativeFullscreen` (player.js, through `pipPresenting`), the chevron's listener and watch.js
`nativePresentationKind` read native's PiP with no added code: one signal, no second predicate. A 360 video is never native-owned, so watch.js's PiP note cannot fire
under native; its reader still answers `'pip'` from the element (bound in the test).

**W3, WebKit source** (WebKit/WebKit @ d761c4ce1bc75dcda0b892372b9872a1374744c2, read 2026-11-05). `requestPictureInPicture`, Source/WebCore/Modules/pictureinpicture/HTMLVideoElementPictureInPicture.cpp:
NotSupportedError (no platform support, :99; the element does not support the mode, :147), InvalidStateError (readyState HAVE_NOTHING, :104; no video track, :109; no window, :115),
NotAllowedError (no transient activation, :121-122; a request in flight, :139). Past the gates it calls `webkitSetPresentationMode` (:145) and keeps the promise.
`webkitSetPresentationMode`, Source/WebCore/html/HTMLVideoElement.cpp: returns NOTHING and refuses silently (:650-655 a mode change in flight; :681 no user gesture via `fullscreenPermitted`, or `supportsFullscreen` false),
so the promise above can stay unsettled forever: that is why the row has a watchdog and not only a catch. `webkitSupportsPresentationMode` (:598-614) is false with no `player()` (:301-304), so WebKit answers no until media is loading: the old one-time check at wire time would have been wrong for it; the row now re-reads at `loadstart` / `loadedmetadata` / `emptied` and when the cog opens.
`HTMLMediaElement::enterFullscreen` (HTMLMediaElement.cpp:8025) also no-ops on suspended playback and queues a task that gives up silently (:8097+). `webkitbeginfullscreen` fires only for standard / in-window modes (:8097-8098), never entering PiP, but `webkitDisplayingFullscreen` (HTMLVideoElement.cpp:534) = `isFullscreen` (HTMLMediaElement.cpp:7951) is true IN PiP, so the rotate bounce's retry loop would have ended PiP: guarded (R4). A reparent is safe: `pauseAfterDetachedTask` (:1258) returns when re-inserted and never pauses PiP (:1267). `disablePictureInPicture` is reflected and FileTube never sets it (no `<video>` in the shells carries it).

**Q3, automatic PiP in Safari: not offered, so Safari is button-only.** WebKit's IDL has `[Reflect] attribute boolean autoPictureInPicture` (HTMLVideoElement+PictureInPicture.idl:37), but a code search of WebKit/WebKit finds it only in HTMLAttributeNames.in, the IDL and one layout test of the reflection, and `autopictureinpictureAttr` has 0 hits: an inert attribute. Not used; the release notes say button-only.

**Safari's failure is NOT root-caused, and cannot be from this box.** Read from source, a loaded inline video in a live tap passes every gate above; the standard call and the presentation call end in the same method, so the new door is not by itself a proven fix. What is measured: a real tap in WebKit does click the row (below), so the plan's click hypothesis is falsified there. What the release changes: the silent catch is gone, so the device check (a) either floats the video or shows the reason on screen. A refusal there is the stop rule (ask Dean, with the name); no patch on theory.

**W3, the probe** (`node scripts/pip-tap-probe.js both`, real server, real clip, Playwright with `page.touchscreen.tap`): `SUMMARY pass=22 fail=0` (11 per engine). WebKit's tap, verbatim: `[{"t":"touchstart","id":"pip-btn","trusted":true,"prevented":false},{"t":"touchend","id":"pip-btn","trusted":true,"prevented":false},{"t":"click","id":"pip-btn","trusted":true}]`, then `[{"call":"webkitSetPresentationMode","arg":"picture-in-picture","inClick":true}]`; under a fake host `[{"type":"video.pip","action":"start","inClick":true}]`. Headless WebKit cannot open a PiP window: Playwright's Linux WebKit answers `pictureInPictureEnabled: undefined` and all three methods undefined, so the methods are recorders, the iPhone platform and coarse pointer are emulated, and the window itself is the device check. iOS's own tap path is not Linux WebKit's; a tap that fails on a phone would still be a device finding.

First pass 25 killed, 7 survived (`pipActive` scope, `pipPost` ownership, detach leaving the prop, a refused exit, the label on browser PiP, a presenting state not clearing the watchdog, the cog's re-read); a test was added for each and all 7 then went red: 32 of 32 killed. `test/unit/native-video-pip.test.js` 24 pass, 0 fail.
