## PRIORITY: item 6 first, and treat it as a data issue

It is the only item that can COST something (disk, and a duplicated library

gate, never slim, and the adversarial seat should be briefed to try to make it

### What was established before the handoff (verified, not assumed)

- There are **two output templates** in `lib/ytdlp/args.js`:
  - `OUTPUT_TEMPLATE = '%(title)s [%(id)s].%(ext)s'` (YouTube lane, :289)
  - `UNIVERSAL_OUTPUT_TEMPLATE = '%(title).100s [%(extractor_key)s=%(id)s].%(ext)s'` (:307)
  Dean's description ("the non-ytdlp id at the end in the yt-dlp folder ... with
  the id in the one for the channel") is consistent with **the same video landing
  under BOTH naming schemes**, which would mean two downloads or a
  download-then-relocate that did not remove the source.
- `maybeRelocate` (`lib/ytdlp/index.js:849`, called at :916 and :1088) moves items
  into channel folders - but **only from the REHEAT path**, not the one-off
  download path. So relocation is not obviously the cause and that assumption
  must be tested rather than inherited.
- Relocation itself is checksum-verified before unlink (v1.41.7), so a partial
  move should not silently duplicate - which makes a second DOWNLOAD the more
  likely explanation.

### First moves for the next session

1. Get the two real filenames from Dean (exact bytes, both paths). The naming
   scheme identifies which lane produced each copy, which is the whole diagnosis.
2. Ask whether the one-off was a **YouTube** URL or a non-YouTube ("universal")
   one - the universal lane has its own template AND its own folder logic
   (`autoUploaderFolder`), and a URL that classifies as universal but resolves to
   a YouTube-ish channel is a plausible double-write.
3. Check whether a **scan** indexed the file at its first path before it moved,
   creating a second `db.metadata` row (the id is `md5(STORED path)` - see
   v1.41.9 - so two paths = two ids = two library entries for one video).
4. Only then decide the fix. **Do not "clean up duplicates" as the fix** - find
   why two files exist. A reaper that deletes the wrong copy is exactly the
   v1.41.6 file-destroyer class this repo already shipped once.

## Item 2 - real view counts (Dean asked "What do you think?")

**Endorsed, with one framing correction.** Verified: view counts today are
**entirely fake** - `getMockViews` (`public/js/common.js:1602`) derives a number
from `md5(mediaId).slice(0,6)` plus file size. yt-dlp captures `view_count`
**nowhere** in `lib/ytdlp/`. So this is a clean new capture, not a change to
existing data.

The correction: a view count captured at download is a **SNAPSHOT of that day**,
and it will drift from reality forever after. That is fine - Dean asked for
exactly that ("taken from the content the day of") - but the UI must not imply
it is live. Recommend rendering it as dated ("1.2M views when downloaded", or a
tooltip with the capture date) rather than a bare "1.2M views" that quietly ages.
Reheat then genuinely re-snapshots it, which is the feature Dean asked for.

Keep the fake STARS (his explicit call). Note the asymmetry in the UI copy so a
future reader does not "fix" the stars to match.
