# v1.82.0 - User avatar + account menu (the v1.81 T8 fast-follow)

Status: ACTIVE - Dean scoped this after v1.81 shipped (2026-08-05). The avatar/
account-menu that split out of v1.81 T8, expanded at intake into a fuller
account surface + a per-user profile photo. Medium-large wave: a new per-user
IMAGE-UPLOAD backend + a cross-shell dropdown component + header/bottom-nav
consolidation.

## Locked decisions (Dean, 2026-08-05 intake)

- **Account menu holds EVERYTHING:** a header (avatar + display name + role), a
  "Change photo" affordance, quick links (Liked, History), Settings, a light/dark
  Theme toggle, and Sign out. It is the one account surface.
- **Avatar = initials monogram by default, with a per-user UPLOADED image that
  overrides it** when set. Initials derive from displayName.
- **Photo upload lives in BOTH places** - a "Change photo" item in the menu AND a
  "Profile photo" Upload/Remove control in Settings->Account - both hitting the
  SAME endpoint.
- **Replace the header Settings link everywhere** - remove the standalone
  `<a>Settings</a>` (only on Home + Watch today); the avatar menu's Settings entry
  is the one top-bar way in (sidebar + bottom-nav Settings unaffected by this).
- **Fold the theme toggle INTO the menu** - remove the header `#theme-toggle-btn`
  from all 9 shells; the menu's Theme item drives the same `toggleTheme()`.
- **Bottom bar: Settings + Theme become DEFAULT-HIDDEN opt-in** - drop them from
  the default bar (they now live in the avatar menu) but KEEP them in the roster
  so a user can still add them. No markup deletion; a defaults-only change.
- **Theme control = the light/dark toggle** (the current header button's job),
  NOT the era/skin picker - era stays in Settings.

## Architect decisions (flag for Dean, made to keep scope sane)

1. **Avatar storage is DISK-ONLY, no schema/settings change** - mirrors the
   custom-logo pattern (`custom-logo.bin`). Per-user file at
   `<DATA_DIR>/avatars/<userId>.bin` (raw bytes). Presence + a cache-bust version
   come from a `statSync` mtime at `/api/auth/me` time; the serve route sniffs the
   mime from magic bytes exactly like the logo serve. So NO migration, and
   avatar metadata never touches the client-writable `settings_json` (whose value
   regex would reject a mime anyway).
2. **Avatar is self-service** - `POST`/`DELETE /api/me/avatar` manage the CURRENT
   user's photo (any signed-in user, their own). `GET /api/users/:id/avatar`
   serves by id (any authenticated user may fetch - a profile photo is low-
   sensitivity, and the admin Users list can show them). A member cannot write
   another user's avatar (there is no by-id write route).
3. **The menu injects from ONE place** - `common.js` mounts the avatar + dropdown
   into `.header-right` on every shell (the established injection pattern at
   common.js ~3086/4905), so the 9 HTML shells only need the Settings-link + theme-
   button REMOVAL, never 9 copies of the menu.

## Task breakdown (each independently green; commit incrementally)

- **T1 - avatar upload/serve/delete (server).** Mirror the logo route:
  - `POST /api/me/avatar` - `express.raw` (allowlist `image/png|jpeg|webp`,
    magic-byte validation, ~1 MB cap), writes `avatars/<req.user.id>.bin` atomically
    (tmp+rename). Self only.
  - `DELETE /api/me/avatar` - unlink the current user's file (idempotent).
  - `GET /api/users/:id/avatar` - read the file, sniff mime (reuse the logo
    sniffer), serve with `Cache-Control` + an ETag/mtime; 404 when absent.
  - `/api/auth/me` (`publicUser`) gains `avatar: { present: bool, version: <mtimeMs> }`
    from a `statSync` (present=false when no file). The client cache-busts the
    `<img>` with `?v=<version>`.
  - Cascade: `deleteUser` (and the restore/replaceAllUsersRaw wipe) must unlink the
    avatar file for a reaped id - no orphaned images. Tests: upload round-trips +
    serves the right mime; oversized/wrong-type/non-image-magic-bytes -> 400;
    DELETE clears; a reaped user's avatar file is removed; a member cannot write
    another user's avatar (no route exists - assert 404/405).
- **T2 - the account-menu component (client).** In `common.js`, at shell boot,
  inject into `.header-right`: an avatar button (an `<img src="/api/users/<myId>/
  avatar?v=<version>">` when `me.avatar.present`, else an initials monogram from
  displayName) + a dropdown. Dropdown sections: (a) header - avatar, name, role,
  "Change photo"; (b) quick links - Liked (`/?liked=1`), History (`/history`);
  (c) Settings (`/setup.html`); (d) Theme (light/dark, calls `toggleTheme()`);
  (e) Sign out. Interaction: click toggles; outside-click + `Escape` close; focus
  management + `aria-expanded`/`aria-haspopup`; the menu is keyboard-navigable.
  Reads `fetchCurrentUser()` (memoized). DESIGN-TOKEN CSS only (the mandatory
  ratchet) - a new `.account-menu*` block in style.css using existing tokens.
- **T3 - wire actions + REMOVE the consolidated header controls.**
  - Sign out reuses the setup.js logout logic (POST /api/auth/logout + clear the
    per-user cap cache + redirect `/login`) - extract it to a shared helper so the
    menu and the Settings button share ONE implementation.
  - Theme item calls `toggleTheme()`; the moon/sun state stays in sync.
  - Remove the header Settings `<a>` from index.html + watch.html.
  - Remove the header `#theme-toggle-btn` from ALL 9 shells; update the
    shell-owned selector list (common.js ~5438) + `setupThemeToggle` (common.js
    ~61) so it no longer requires the header button (the menu drives it now).
- **T4 - photo upload UI (both entry points).** A "Change photo" item in the menu
  and a "Profile photo" Upload/Remove control in Settings->Account (setup.html /
  setup.js, beside the existing account chip + Sign out). Both POST the file to
  `/api/me/avatar` (client reads the raw file, sends it as the body with the right
  Content-Type - same as the logo uploader), then refresh the avatar (bump the
  cache-bust version). Remove -> DELETE. Honest errors on 400 (too big / not an
  image) via `showToast`.
- **T5 - bottom-nav: Settings + Theme -> default-hidden opt-in.** Add `'settings'`
  and `'theme'` to `BOTTOM_NAV_DEFAULT_HIDDEN`; drop the `BOTTOM_NAV_COMPAT_TAIL =
  'settings'` pin (so settings is no longer force-appended) - carefully, so a
  user's SAVED custom layout that includes them is preserved (opt-in kept). They
  stay in `BOTTOM_NAV_OPTIONAL` (still addable in the customizer). Update the
  bottom-nav tests + the CONTRIBUTING/roster docs if they assert the old defaults.

## Acceptance criteria

- **AC1** A signed-in user sees an avatar top-right on every shell: their uploaded
  photo if set, else an initials monogram. Tapping it opens the account menu.
- **AC2** The menu contains account (name + role), Change photo, Liked, History,
  Settings, a working light/dark Theme toggle, and a working Sign out.
- **AC3** `POST /api/me/avatar` accepts only png/jpeg/webp within the size cap
  (magic-byte validated); anything else 400s. The image round-trips through
  `GET /api/users/:id/avatar` with the correct mime. `DELETE` reverts to the
  monogram. No schema migration.
- **AC4** A member can set only their OWN avatar; there is no by-id write route.
  A reaped user's avatar file is unlinked (no orphans).
- **AC5** The header Settings link and the header theme toggle are gone from every
  shell; the menu carries both. Sign out shares ONE implementation with Settings.
- **AC6** Bottom bar: Settings + Theme are default-hidden but still addable; a
  user's previously-saved layout that included them is unchanged.
- **AC7** Design-token census stays at zero (the new menu/avatar CSS uses tokens).

## Named attack surfaces (for the gate - full two-reviewer gate: new upload surface)

- **S1** `POST /api/me/avatar`: a non-image with an image Content-Type (magic-byte
  bypass), a >cap payload (does the raw limit reject before buffering?), a
  zero-byte / truncated image, a `Content-Type` the allowlist misses. Prove each
  400s and writes nothing.
- **S2** Cross-user write: any path to set ANOTHER user's avatar (there must be
  none); the serve route must not accept a write verb. Path-traversal via `:id`
  (`../`, non-numeric) on the serve route -> must not escape the avatars dir.
- **S3** Serve route leaks: does `GET /api/users/:id/avatar` leak existence/other
  data for a non-existent id? Cache headers correct? No arbitrary-file read.
- **S4** Orphan/lifecycle: delete a user -> avatar file gone; restore/replaceAll ->
  no stale image bleeds to a reassigned id.
- **S5** The removed header controls: prove theme toggle + Sign out + Settings all
  still reachable and working via the menu on EVERY shell (no shell left without a
  way to toggle theme / sign out). The bottom-nav default change must not strand a
  user who had ONLY the bottom-nav Settings.
- **S6** Menu a11y/interaction: outside-click/Escape close, focus trap sanity, no
  double-mount across SPA nav (the `#view-root`-swap class), injected once per shell.
