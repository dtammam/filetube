## Root causes (from the v1.52/v1.53 code, verified in-tree)

- The v1.53 optimistic subscribe render runs INSIDE setupSubscribeButton
  at HYDRATION - never in the v1.52 seed pre-paint frame. Warm cache
  still means a visible pop at hydration time.
- Pin is rendered only after the real health+subs+pins fetch chain -
  always a beat behind Subscribe, hence the second pop.
- A STALE cached subs list (cached before Dean subscribed; 5min TTL)
  optimistically labels "Subscribe", then the real fetch corrects to
  "Subscribed" - the literal flash he reported. The cache has no
  write-through on the subscribe/unsubscribe/pin mutations.
- applySubscribeButtonLabel itself is atomic (text+class together) - the
  flash is state-freshness, not render-ordering.

## Track A - kill the FOUC

1. CACHED-STATE-FIRST SETUP: restructure setupSubscribeButton/
   setupPinButton into one `renderSubscribeAndPin(item, {subs, pins,
   confirmed})` renderer + handler-wiring (wired once per view instance,
   guarded). At HYDRATION: if the capability cache is warm, render+wire
   from CACHE synchronously, then revalidate in the background and
   re-render only on difference. At INIT (v1.52 seed path): a FULL seed
   + warm cache renders both controls in FRAME ONE (the seed item is
   metadata-shaped; decideSubscribeButtonState needs only channelUrl).
2. WRITE-THROUGH: every mutation that changes the cached answers
   updates the cache in the same success handler - subscribe (POST),
   unsubscribe (DELETE), pin/unpin. A warm cache can then only be
   seconds stale, and the Subscribe->Subscribed flash dies except in
   the cross-device case (disclosed; the background revalidate corrects
   it in ~1 RTT as designed).
3. Row shift: with frame-one rendering the warm-cache path never
   reflows. COLD cache (first visit of a tab) keeps the additive
   appearance - disclosed residual, plus a CSS guard: the subs chip
   gets max-width + ellipsis so track B's longer real label cannot push
   the Subscribe button down a row (device probe).

## Track B - real subscriber counts (the approved parked spec)

- Field names: `sourceFollowerCount` + `sourceFollowerCountCapturedAt`
  (collision-grepped clean; the v1.48 lesson).
- Capture: `channel_follower_count` joins BOTH print templates
  (args.js, same fixed-literal `.{...}j` posture as view_count);
  parseChannelMetaLine carries it via presentNumeric (NOT `present` -
  the v1.47.4 dead-on-arrival class); repullItemMetaAndSubs Pass A
  re-snapshots it (the flame button refreshes it for free).
- Store: `parseCapturedFollowerCount` (integer >= 0, generous 1e12
  ceiling - a mirror of parseCapturedViewCount); recorded in BOTH
  downloadMeta lanes; consumed in both consumers as a UNIT with the
  entry's own capturedAt (the view-count pattern verbatim).
- Server: ONE shared writer `applyCapturedFollowerCount(item, consumed,
  nowMs)` called at ALL THREE consume sites (v1.41.4 discipline);
  carry-forward matrix: re-init carry, Phase-2 completed-adoption +
  partial-reheat gap-fill, reheat SUPERSEDE. NO monotonicity guard for
  followers (unlike views): subscriber counts legitimately fall, and a
  reheat is a deliberate refresh - decided here, disclosed.
- Client: `resolveSubscriberLabel(item, channelName)` in common.js -
  real count -> `formatCompactCount(n)` ("24K", "1.2M", YouTube-style)
  + ` subscribers as of YYYY-MM-DD` (ISO, from capturedAt); no captured
  count -> the existing getMockSubCount fallback (unchanged posture).
  Consumed by deriveWatchPaintPlan (the v1.52 pure painter - seed and
  hydration cannot disagree by construction; list items carry the new
  fields via the full-spread posture for free).
- ALSO: `formatViewCountCaptureDate` switches to ISO YYYY-MM-DD
  (approved with the spec; the affected view-count label tests update
  in the same commit as deliberate lock changes).

## Known gaps / accepted residuals

- Cold-cache first visit still shows the additive control appearance
  (no wrong content, controls arrive once) - the capability is genuinely
  unknown; disclosed.
- Follower counts have NO monotonicity guard (unlike views) - a
  degraded 0-follower read could land; the flame button re-fetches.
  (Gate round 1, adversarial S5) The BATCH reheat supersedes through the
  identical recordRepulledItemMeta path, so the same applies there - and
  the degraded-read risk is narrow: a bot-check yields no JSON or a null
  field, both of which parse to null and skip; only a literal numeric 0
  lands. Disclosed; revisit if observed.
- Existing items get real counts only via reheat (capture is
  download-time); the mock remains for everything else - by design.
- (Gate round 1, QA S1) A reheat landing between a list fetch and a tap
  can flip the subs label from mock to real at hydration (seed painted
  from a stale list item without sourceFollowerCount). Mirrors the
  accepted view-count seed behavior; one repaint, correct value wins.
- (Gate round 1, QA W3) The pin toggle's synchronous cache write-through
  is merge-only: if cache.pins was never populated, the sync write is
  skipped (a synthesized one-entry array would under-render the pinned
  sidebar prime). refreshPinnedSidebar's fetchAllPins in the toggle's
  .finally backfills the merged pins authoritatively one round trip
  later either way - the residual is a sub-second window on a
  first-ever toggle in a fresh tab.
