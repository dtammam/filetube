# v1.358: drag down while holding to lock the 2x

Written 2026-10-02 by the Sonnet builder-session (v1.357) at main e6840db5, for the next Sonnet session. ROADMAP Planned
"Idea: lock the hold-to-speed-up by dragging down" is the WHAT; this plan is the HOW. Small and self-contained: one gesture in
`public/js/player.js`, one pill state, no server, no storage, no new dependency.

## 1. The outcome (what Dean will do on device)

1. Phone, a playing video or audio item in the full player: press and hold the picture, 2x starts (today). Without lifting,
   drag the finger DOWN a short way: the 2x pill changes to a locked state (a lock mark, still "2x") and the finger can lift:
   playback STAYS at 2x.
2. While locked, one tap on the pill unlocks it and playback returns to the speed it had before the hold. The same press-and-hold
   still works as today (hold, lift = back to normal speed) when the finger never drags down.
3. A hold that drags sideways or up behaves exactly as today. A vertical page scroll inline, the swipe-back (off in fullscreen,
   v1.337) and the 15 s double-tap skip are not disturbed.

## 2. Rulings and defaults

| # | Question | Ruling |
|---|---|---|
| R1 | The drag that locks | While `holdActive` and the finger is down, a downward drag of at least `LOCK_DRAG_PX` (default 48) from the touchstart point whose vertical travel exceeds its horizontal travel. Architect default; one named constant. |
| R2 | The locked look | The existing `#speed-badge` pill gains a locked state (class `is-locked`): a lock glyph beside "2x" (the sprite in `public/js/icons.js` has NO lock mark today: W2 adds one the way that file adds every glyph, both of its style sets, and runs whatever icon census exists). Dean: "lock it", so the state must be visible. Architect default. |
| R3 | How to unlock | One tap on the pill (it takes `pointer-events` only while locked). Also released, as today's hold is, by `resetTransientPlaybackUi()` (dock, close), by entering native fullscreen, and by a NEW item loading. Architect default. |
| R4 | Does pause release it | No. Pausing and resuming keep the lock; only R3's paths release it. If the media ends and the next item starts, that is a new item (released). Architect default. |
| R5 | What speed it returns to | `prevRate`, the rate before the hold, exactly as `releaseHold` restores today. The lock is TRANSIENT: it touches only `playbackRate`, never `defaultPlaybackRate`, never `ft-rate`, never the speed button (stop rule d). |
| R6 | Scope | Touch only (the hold gesture is touchstart-armed). Faux fullscreen and inline alike (the hold already works in `STATE_FULL`, not docked, not native fullscreen). Desktop mouse hold does not exist and is out of scope. |
| R7 | Haptic | None. The pill change is the feedback. Architect default. |

## 3. Research to do first (W0 measures; nothing here is assumed)

1. Does a `touchmove` keep arriving at `#media-player` / `#audio-bg-art` after the 500 ms hold latches, in headless Chromium with
   touch emulation (CDP `Input.dispatchTouchEvent`)? The existing listener returns early on `holdActive`, so nothing reads the
   drag today. On iOS Safari the page may start scrolling or the touch may be cancelled by a vertical pan; the listener is
   `passive: true` so it cannot stop a scroll. Measure inline (page taller than the viewport) whether the page scrolls while the
   hold is active, and what `touch-action` the surfaces carry (`grep -n "touch-action" public/css/style.css`). If a drag-down
   scrolls the page, the lock needs `touch-action: none` on the surface WHILE `holdActive`, set by class at engage and removed at
   release (never permanent: it would break a plain page scroll that starts on the video). Record the measured behaviour.
2. The swipe-back (public/js/common.js ~10456-10490, v1.337: not in fullscreen video) and the pull-to-refresh: confirm a
   downward hold-drag does not start either (pull-to-refresh is a downward drag at scrollY 0).
3. The touchend path: today `touchend` with `holdActive` does `preventDefault()` + `releaseHold()` + `lastTapTime = 0`. A locked
   hold must skip `releaseHold()` but still `preventDefault()` and zero the tap state (no stray pause or skip from the lift).

   branch (a falsifier that cannot fail proves nothing, LESSONS 3).

### W1 - The lock (R1, R3, R4, R5)
1. State: `holdLocked`, cleared in `releaseHold()` and in every path that clears `holdActive`. A new function `lockHold()` sets it
   (only when `holdActive`), sets the badge locked, touches ONLY `playbackRate` (already 2).
2. `touchmove`: while `holdActive`, call the pure decision with the drag from `startX/startY`; on `'lock'` call `lockHold()` once.
3. `touchend`: if `holdActive && holdLocked`: `preventDefault()`, `lastTapTime = 0`, return WITHOUT `releaseHold()`. A
   `touchcancel` still releases (a cancelled touch must never strand 2x; it also covers the browser taking the touch for a scroll).
4. Unlock: a tap on `#speed-badge` while locked calls `releaseHold()`. `resetTransientPlaybackUi()` and `onEnterFullscreen` already
   release; confirm `holdLocked` clears there. A new item: confirm `teardownMediaState`/`load()` resets the rate AND the badge
   state (if only the rate resets, the pill would lie: add the clear in the one load path, bound by a test).
5. Tests (each mutated red, recorded): lock on a down-drag; a plain hold unchanged; sideways and up drags do not lock; touchend
   keeps 2x when locked; touchcancel releases a locked hold; the badge tap unlocks and restores `prevRate`; dock/close/fullscreen/new
   item release; the lock never touches `defaultPlaybackRate` or `ft-rate`; pause/resume keep it.
