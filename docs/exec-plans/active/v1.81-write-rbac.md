Status: ACTIVE - Dean scoped this after device-testing v1.80 (2026-08-05). The
follow-up to the v1.80 RBAC *visibility* wave: v1.80 controlled what a member can
SEE; v1.81 controls what a member can DO (mutate) and makes the client tell the
truth when the server says no. SECURITY/DATA-SAFETY sensitive (destructive
routes) -> FULL two-reviewer gate, never slim.

Intake settled with Dean (2026-08-05):
- **Workflow:** write plan, then build (plan committed for async review; not blocked).
- **`POST /api/videos/:id/view`:** LEFT UNGATED (play-count ping; a member must
  record views).
- **`POST /api/videos/:id/dimensions`:** LEFT UNGATED - it is a player-driven

## The five tasks (Dean's scope, refined by the code)

1. **Write-RBAC** - a new per-user capability `canModifyLibrary`, default OFF for
   members (sibling to the existing `canManageSubscriptions`). Server-gate the
   content-mutating routes a member can currently hit. Admin always can.
2. **Honest-denial UI (systemic sweep)** - make every mutating client action
   reflect the real result (short "you don't have permission" message on 403, no
   phantom removal) and HIDE the delete/move/edit affordances for a member without
   `canModifyLibrary`.
   > FRAMING CORRECTION (from the client-surface map): the client does NOT broadly
   > fake success - almost every mutating call-site already awaits the response and
   > gates the DOM change on `res.ok`/`data.success`. The real gaps are (a)
   > INCONSISTENT error handling (toast vs blocking `alert()` vs SILENT
   > `console.error`) with NO 403 special-case anywhere, and (b) affordances shown
   > to a capability-less member. So T6 is "unify error paths + add a 403 message +
   > hide affordances," not "stop optimistic removal." Report this honestly to Dean.
3. **Stats scoped per-user (#127a)** - `/api/stats` inventory sub-counts + watch
   aggregates must reflect only the member's visible library + their own watch
   data. v1.80 filtered content titles/counts but left `computeInventory`'s
   `progress/viewCounts/liked/folders/deleteTombstones/users` raw.
4. **Empty-state text everywhere** - one shared empty-state, applied to every
   video folder / playlist / library / liked / history / search / music view that
   can render empty. No blank surfaces (the treatment books/podcasts already have).
5. **User avatar + account menu** - a YouTube-style top-right avatar opening an
   account/settings menu. BUILT LAST (after 1-4) so it can spin off into a
   v1.82 fast-follow if it grows. May split.

## Locked / derived decisions

- **Capability name:** `canModifyLibrary` (column `can_modify_library`), sibling
  to `can_manage_subscriptions`. Default `0`. Admin (`role === 'admin'`) bypasses
  it entirely, exactly like the visibility model.
- **Existing members lose delete/move/edit** until an admin grants the flag -
  Dean approved. Admins are unaffected (role bypass; the column default never
  gates them).
- **Downloads stay under `canManageSubscriptions`** (unchanged). Subscription /
  channel-registry mutation stays under `canManageSubscriptions`. `canModifyLibrary`
  governs LIBRARY CONTENT mutation (delete/move/edit media, trash lifecycle,
  scans, cache-clear).
- **No third role** (admin | member only), consistent with v1.80.

## THE gate helper (single decision point - the v1.41.4 one-writer scar)

`requireModifyLibrary(req, res)` in server.js, modeled EXACTLY on the existing
`requireManageSubscriptions` (server.js ~5587):

```js
function requireModifyLibrary(req, res) {
  if (req.user && (req.user.role === 'admin' || req.user.canModifyLibrary)) return true;
  res.status(403).json({ error: 'You do not have permission to modify the library.' });
  return false;
}
```

Every gated route calls it as the FIRST guard, before `restrictedVideoMutation`
and `refuseIfReadOnlyMedia`. Order rationale: a member without the capability
gets a uniform 403 and never reaches the existence-revealing 404 path of
`restrictedVideoMutation` (avoids a capability-less member probing which ids
exist). For routes that live in the ytdlp/podcasts modules, thread the predicate
through the deps bundle exactly as `requireManageSubscriptions` is (deps.
`requireModifyLibrary`).

- `restore`/backup admin routes already `requireAdmin`.

> The exact set is bound by the census/classification test (T-CENSUS below):
> every live mutating route is classified `personal | library-write |
> manage-subs | admin | public`, and the suite fails if a NEW route is

## Acceptance criteria (the census + stats tests bind most)

- **AC1** A member without `canModifyLibrary` (and not admin) gets **403** on
  every `library-write` route (video delete/move/chapters/attribute-channel,
  trash restore/purge, scans, cache-clear, podcast episode delete). Admin and a
  member WITH the flag succeed.
- **AC2** A member's OWN personal-state routes (un-like, history, watched, queue,
  pins, progress, view, dimensions) are UNAFFECTED - still 2xx.
- **AC3** The classification is COMPLETE - a new mutating route fails the census
  suite until classified (the forcing function).
- **AC4** The client never phantom-removes on a 403/404: the item stays, a
  permission message shows. Affordances are HIDDEN for a capability-less member.
- **AC5** A restricted member's `/api/stats` shows only visible-library +
  own-watch counts; no global inventory totals, no other users' data, no
  `users`/`deleteTombstones` system counts. Admin stats byte-unchanged.
- **AC6** Every empty list/grid view renders the shared empty-state; no blank
  surface anywhere.
- **AC7** Existing single-admin installs are behavior-unchanged (admin bypass;
  column default irrelevant to admins). No data migration beyond the additive
  column.
- **AC8** Prototype/coercion-safe: `canModifyLibrary` is strictly boolean-coerced
  server-side; a truthy-string body value cannot grant it.

## Named attack surfaces (brief the adversarial seat to make a capability-less member MUTATE content)

- **W1** Direct-URL hit on every `library-write` route as a member WITHOUT the
  flag - video delete/move/chapters/attribute-channel, trash restore + purge,
  all three scans, cache-clear, podcast episode delete. Prove 403, prove the item
  is byte-unchanged on disk/db after.
- **W2** Guard-ORDER bypass: does `requireModifyLibrary` truly run BEFORE any
  side effect / before the 404 existence oracle? Mutation-test by neutering the
  guard - the census test must go red.
- **W3** Capability injection via `POST /api/users` / the PATCH route:
  `canModifyLibrary: "true"` (string), `1`, `[]`, `{}` - only a strict boolean
  `true` grants it (AC8). Self-grant: can a member escalate their OWN flag via any
  route? (Only admin routes may set it.)
- **W4** The podcast episode delete re-gate: a member with `canManageSubscriptions`
  but NOT `canModifyLibrary` must now be 403 on episode delete (it moved gates) -
  and still 403 without either. A member with `canModifyLibrary` succeeds.
- **W5** Personal-state false-positive: confirm the gate did NOT accidentally
  catch a member's own un-like/history/queue/progress (AC2) - those must stay 2xx.
- **W6** Client honest-denial: force a 403 (member without flag) and confirm NO
  phantom DOM removal, message shown, item still present on reload. Confirm the
  affordance-hide is not just CSS (a member can't re-issue the fetch from a hidden
  button via console AND have it succeed - server is the real gate).
- **W7** Stats leak residual: a restricted member's `/api/stats` must not leak a
  global count that reveals restricted-content or other-users' volume (#127a).
- **W8** A NEW mutating route added without classification (prove the census
  catches it) - the v1.80 S7 pattern for writes.
