# v1.75.0 - Liked consolidation + bottom-bar freedom

Status: ACTIVE (prepped 2026-08-03 by the outgoing session; execution by a
new session at Dean's invocation). This plan doubles as the reviewers' spec.

## Problem framing (Dean, 2026-08-03, verbatim intent)

1. "Remove liked section for podcasts (and for songs if it exists). It all
   gets centralized under the one central Liked (it's currently there)."
2. "In bottom bar, Home is not always left-most bound. It's also not an
   option in Bottom bar, add as an option."
3. "Add liked as a bottom bar option as well. And settings. And make
   sort-able."

Interpretation (confirm at kickoff, see Open rulings): the central
mixed-kind Liked playlist (v1.72's headline: /?liked=1 renders episodes +
tracks + books + videos via /api/liked) makes the per-kind Liked surfaces
redundant - they show a SUBSET with their own quirks (tech-debt #93: the
podcasts card/lane count disagreement + silent 100 cap). Remove the
redundant per-kind UI surfaces; likes themselves (hearts, data, API) stay
untouched. And the bottom bar's two hard-bound anchors (Home first,
Settings last, both un-hideable) retire: Home, Settings, and a NEW Liked
entry become ordinary optional entries - sortable and hidable like the
other nine.

## Design

### D1: per-kind Liked surface removal
- podcasts.js: remove LIKED_LANE, buildLikedCard, openLiked and the
  `__likedLane` routing arms. The podcasts place shows only real shows.
- music.js/music.html: remove the Liked tab (strip declaration + the three
  known arms + whatever the grep enumeration finds; a deep link to the
  removed tab must fall back cleanly to the default tab, not blank - the
  SPA lesson: test in-app nav AND direct URL load).
- CLOSES tech-debt #93 by removal (update the tracker row: CLOSED, "the
  lane is gone; the central Liked is the one surface").
- docs/CONTRIBUTING.md capability matrix: the per-kind "likes lane"
  parentheticals for podcasts/music must be re-worded to point at the
  central Liked (keep the honest-parenthetical rule; do not soften).

### D2: bottom bar - anchors retire, three entries join
- `BOTTOM_NAV_FIXED_FIRST`/`BOTTOM_NAV_FIXED_LAST` retire. `home`,
  `settings`, and NEW `liked` join `BOTTOM_NAV_OPTIONAL` (12 ids after).
- COMPAT (the load-bearing subtlety): existing configs know nothing of
  home/settings in `order` and pre-date `liked`. An untouched config MUST
  render today's exact bar: home first, current middle order, settings
  last, no liked. Fix shape: when `order` lacks `home`, it sorts first;
  when it lacks `settings`, it sorts last; `liked` joins
  `BOTTOM_NAV_DEFAULT_HIDDEN` (opt-in via `shown`, the v1.72 posture).
  This is resolveBottomNavLayout logic, unit-tested against: empty config,
  pre-v1.71 config (no shown key), v1.74-era config (order without
  home/settings), and a post-v1.75 config exercising all three new ids.
- FLOOR: hiding every entry leaves an empty fixed bar. Ruling R2 below
  (recommendation: >=1 visible entry enforced at the Settings UI, and
  resolveBottomNavLayout falls back to the default layout when the
  resolved visible list is empty - both sides, belt and suspenders).
- The new `liked` bottom-nav item: `<a href="/?liked=1" ... data-nav="liked">`
  in ALL NINE shells (enumerate by grep; every shell that carries
  data-nav="home" gains the sibling). Glyph: the heart from the existing
  icon pipeline, the v1.73.2 Books-glyph pattern (single-asset posture,
  CSS/icon-set delivery, emoji-set fallback INCLUDED UP FRONT - the v1.73
  W2 lesson; never a raw emoji codepoint in markup, the v1.38 lesson).
- Count-gating: the SIDEBAR Liked entry stays count-gated; the bottom-bar
  entry is NOT count-gated (explicit user opt-in is the gate) - ruling R3.
- setup.html/setup.js: the customization panel lists all 12, its copy
  drops the "Home stays first and Settings stays last" promise, and the
  active-nav highlight for `liked` works on /?liked=1 (check
  active-nav-item.test.js's contract; `home` and `liked` share the `/`
  path - the highlight must discriminate on the query, name this in tests).

### D2-bis: ADDENDUM - the CSS order ladder (found during T2, 2026-08-03)

Machine-derived at implementation time, and it reframes Dean's ask #2. There
was a live flex-`order` ladder in `public/css/style.css` (~4215, inside the
`@media (max-width: 768px)` block, from v1.39.2):

    #bottom-nav [data-nav="home"]  { order: 1; }  ... settings { order: 7; }

Seven ids were pinned; every id added AFTER v1.39.2 - history (v1.64),
podcasts (v1.71), music/books/downloads (v1.72/v1.73) and the new liked -
carried the flex default `order: 0` and therefore rendered to the LEFT of
Home. That is Dean's sentence verbatim: "In bottom bar, Home is not always
left-most bound." His ask #2 is a BUG REPORT, not only a feature request;
this plan's original reading (a) was half the story. On a default install the
bar rendered `History | Home | Playlists | [Download] | [Subs] | Light/Dark |
Settings`.

Worse: CSS `order` beats DOM order outright, so v1.44 T12's reorder feature
could never move any of those seven items - the customization panel has been
lying about the bar's sequence since v1.44. No test bound the ladder (grep:
zero hits in test/), which is why it survived.

RESOLUTION (both readings are served by one fix): the ladder is DELETED and
`resolveBottomNavLayout` + `applyBottomNavCustomization` become the sole
authority on sequence, locked by test/unit/bottom-nav-order-authority.test.js
(which also proves the USE, in a jsdom bar, not just the decision).

CONSEQUENCE, disclosed and NOT hidden behind the compat promise: an untouched
device's bar does change - History moves from far-left to third, and with the
yt-dlp module on, Light/Dark moves left of Download/Subs. Membership and
opt-in state are still byte-identical (that is what the differential oracle
test binds); ORDER changes exactly where the CSS was overriding the resolver.
This partially overrides ruling R4's "the default look is unchanged" - the
alternative was shipping the wave's headline ("make it sortable") on top of a
CSS layer that pins 7 of 12 positions. Dean's call to revert if he wants
History left-most.

GLYPH deviation from D2: the new item uses `icon-star`, not the heart D2
suggested. The bottom-bar Liked and the SIDEBAR Liked are the same
destination (`/?liked=1`) and the sidebar entry mints `icon-star`; matching
it also means zero new icon CSS, because `.icon-star` is the one glyph
deliberately identical across all four data-icons sets (style.css AC8) -
which covers the emoji set up front (the v1.73 W2 lesson) without touching
any existing heart surface.

  WITH them, and no test goes vacuous (the divergent-fixture class).

- setup.js floor enforcement (can the UI produce an all-hidden config?
  what renders if localStorage is hand-edited to hide all 12?).

Gate pacing: 2 rounds per seat, then ship on CRITICAL/WARNING closure and
