# v1.49 - Per-video reheat ("Refresh metadata" on the watch page)

Status: ACTIVE
Owner: main session (lean mode)
Gate: FULL two-reviewer gate, never slim. This feature can MOVE and DELETE
media files (the relocation half) and Dean has no media backup. The
adversarial seat is briefed to destroy the data.

## The ask (Dean, intake 2026-07-28)

> I'd want the ability to, on a specific video, force a reheat. I'd want it to
> check to see if it's a YouTube video and if so associate in a video with the
> channel name. Refresh the view count. All the other works etc. On a video by
> video basis.

Today the reheat is library-wide only: `POST /api/ytdlp/repull-metadata` takes
one body field (`force`) and enumerates all of `db.metadata`. There is no
per-item trigger anywhere, in the UI or the API.

## Intake decisions (numbered as asked, Dean's answers)

1. **One button**, and it covers BOTH halves - metadata hydration AND the
   physical relocation into the channel folder - with the move behind an
   explicit confirm that states the destination and the transfer method
   (hard link vs cross-filesystem copy) before anything is touched.
2. **The v1.48 view-count monotonicity guard is overridden on this path only.**
   An explicit single-video force is a human looking straight at one item, so a
   downward correction is allowed here. The library-wide batch keeps the guard
   exactly as shipped (tech-debt #60 stays open for the batch).
3. **Non-YouTube videos**: still run the local, network-free ffprobe tags pass,
   then report honestly ("No YouTube identity found, nothing to refresh").
   Never a silent success. The existing embedded-tag trust gate is unchanged -
   a ripped CD track never gets its title overwritten by its ID3 tag.
4. **Feedback**: 202 + the existing activity one-shot. The watch page polls
   `GET /api/subscriptions/status`, refreshes its metadata in place, and toasts
   what actually changed.
5. **Collision with a library-wide reheat**: share the existing
   `repullMetadataInProgress` latch. 409 both ways.
6. **Permissions**: match the current yt-dlp routes (auth wall, no admin gate).
   RBAC is the v1.42 multiuser tranche's job, not a one-off gate here.
7. **Entry point**: watch page only for v1.

## Architectural constraints this plan is built around

**A. Anti-drift is the load-bearing property of this subsystem.** v1.41.7
established ONE decision function (`planImportRelocation`) shared by the
preview and the executor, precisely so a preview can never lie about what a
move will do. The per-video path must extend that discipline, not fork it:

- Eligibility comes from `enumerateRepullableItems` (the whole-library
  enumerator), filtered to one id. NOT a second, per-item eligibility copy.
  Cost is one O(N) pure pass per click, no I/O. Accepted deliberately.
- The per-item reheat body is EXTRACTED out of `runRepullMetadataBatch` into
  one function both callers use. The batch must not keep a private copy.
- The confirm dialog's contents come from `planImportRelocation` - the same
  function the executor calls - so the dialog cannot describe one thing and
  the move do another.

**B. The relocation re-keys the item.** `getMediaId` hashes the file path, so
a successful move changes the id. The response must return `newId` and the
watch page must navigate to it (the same pre-navigate step
`handleMoveClick`/`performMediaDelete` already do, or the persistent player
keeps Range-requesting a dead id).

**C. SPA mount trap (tech-debt #34).** The v1.41.7 relocation-preview modal
shipped broken for exactly this reason: its markup lived outside `#view-root`
and its styles in a page-local `<style>`, so in-app navigation never mounted
it. This confirm dialog is built at RUNTIME and appended to `document.body`
(the `showConfirmModal` pattern), with any new styles in `public/css/style.css`.

**D. `showConfirmModal` interpolates its body with `innerHTML`.** The confirm
body here carries a filesystem path and a channel name - both attacker/
filename-influenced. Either escape at the call site with the existing
`escapeAttr`-grade helper or (preferred) give the modal a node-accepting body.

## Work breakdown

### T1 - Extract the per-item reheat body (no behaviour change)

`lib/ytdlp/index.js`: pull the loop body of `runRepullMetadataBatch` (the
local ffprobe pass, watch-URL derivation, network pass, precedence merge,
avatar memo, `markComplete`/`exhausted` computation, the
`hasAnythingToPersist` OR-chain, the `recordRepulledItemMeta` call) into

```
async function reheatOneItem(deps, config, item, opts)
  -> { outcome: 'done'|'skipped'|'failed', recorded, youtubeId, watchUrl,
       changed: {...}, exhausted, markComplete }
```

- `opts.avatarMemo` is the batch's `Map`; the single-item caller passes a
  fresh one (one probe, then discarded).
- `opts.allowViewCountDecrease` threads decision 2 through to
  `recordRepulledItemMeta`.
- **Relocation stays OUT of this function.** The batch calls `maybeRelocate`
  exactly where it does today (gated on `recorded`, after the persist); the
  single-item route instead PROPOSES it. The stale-mediaId ordering note at
  the existing call site must survive the extraction.
- The batch keeps all counting and every `activity.setOneShot` call.

Tests: the existing reheat suite must pass untouched. Add a characterization
test asserting the batch and the single-item path produce identical persisted
state for the same item (the anti-drift lock).

### T2 - `recordRepulledItemMeta`: opt-in view-count decrease

`server.js`. Add `meta.allowViewCountDecrease === true` (default false, so the
batch is byte-identical in behaviour). When true, an accepted count supersedes
regardless of direction, still through `parseCapturedViewCount` and still
writing count+date as a unit.

Tests: batch path refuses a decrease (existing behaviour, locked); the
single-item path accepts one; an INVALID value is still refused on both.
Mutation-verify: flipping the default to true must fail a test.

### T3 - `POST /api/ytdlp/repull-metadata/item/:mediaId`

`lib/ytdlp/index.js`.

- `refuseIfReadOnlyMedia` first (safe mode).
- 409 if `repullMetadataInProgress`; set the same latch for the duration of
  this single run so a library batch cannot start underneath it.
- `enumerateRepullableItems(db, config)` filtered to `:mediaId`; 404 with a
  reason when the id is not present.
- 202 `{started: true, mediaId}`, then run `reheatOneItem(..., {force: true,
  allowViewCountDecrease: true})` in the background under a DISTINCT activity
  one-shot id so it never collides with a library batch's entry.
- On completion write the outcome into the activity entry: what changed
  (channel name, view count before/after, title, subtitles, chapters,
  release date), plus the relocation PROPOSAL from
  `planImportRelocation(deps, config, mediaId)`:
  `{available, destinationPath, transfer, sameDevice, reason}`.
- Nothing on this route moves a file.

### T4 - `POST /api/ytdlp/repull-metadata/item/:mediaId/relocate`

The confirm step. Safe-mode gated, latch-gated, calls
`relocateHydratedImportIntoChannelFolder` and returns `{status, newId,
newPath, archived}`. `archived: false` is surfaced to the user, not buried -
the file is fine but a subscription poll may re-download it.

### T5 - Watch page button + flow

`public/js/watch.js`, `public/css/style.css`.

- `setupRefreshMetadataButton()` mounted into `.watch-action-btns` beside
  Move, same `.btn` + `.icon-*` + `.btn-label` conventions, idempotent guard,
  `{signal}`-bound listener (the v1.41.11 staleness lesson).
- Visibility gated on the yt-dlp module health probe (`GET
  /api/subscriptions/health`), latched, mirroring
  `probeAndReconcileRepullButton`.
- Click: POST, disable the button, poll `GET /api/subscriptions/status` for
  the one-shot, then toast the diff and re-render the affected page bits.
- If `relocation.available`, open the confirm dialog (destination + transfer
  method + size when a copy), buttons "Move it" / "Leave it where it is".
  Confirm: POST relocate, then navigate to `newId`.

### T6 - Suites on both Node versions, then the full gate

## What actually landed, including the deviations from this plan

Recorded here rather than quietly absorbed, so the gate reviews the real
shape of the change.

1. **Dean revised T5's design mid-implementation**: the control is a small
   flame-glyph button inline with the other five action-row buttons (same
   `.btn` token, same icon + `.btn-label` shape, row stays one line), not the
   text button this plan first described.
2. **`flame.svg` is a FileTube original**, not a Material asset - there is no
   Material glyph for "reheat" worth borrowing, and mis-attributing a
   hand-drawn path to Google would be a licensing lie. Documented as such in
   `public/assets/icons/README.md`. No renderer was available in this
   environment, so the glyph was verified by rasterising the path to ASCII
   rather than by eye. **It has never been seen at real size in a browser -
   Dean's device pass is the arbiter of how it actually looks.**
3. **New field: `outcome` on the activity entry.** `state` is a lifecycle
   marker and reads `'done'` for a job that finished having FAILED its item,
   so a client branching on `state` would have reported success for work that
   did not happen. `outcome` (`done` / `skipped` / `failed`) is what the
   client branches on.
4. **The `'running'` activity write now explicitly clears `before`/`after`/
   `relocation` and stamps `mediaId` from the start.** `activity.setOneShot`
   MERGES into a fixed key, so without this a client polling mid-run would
   read the PREVIOUS video's relocation proposal and could be offered a move
   belonging to a different file. Found by self-review, not by the gate.
5. **`repullMetadataJobKind`** was added so the existing cancel route stops
   claiming `{cancelled: true}` for a single-video run it cannot actually
   cancel.
6. **`showConfirmModal` gained an optional `labels` argument** so the
   irreversible move reads "Move it" / "Leave it where it is" instead of
   "Confirm" / "Cancel". Additive; every existing call site is unchanged.
7. **Two pre-existing icon tests were loosened** (`card-like.test.js`,
   `shuffle-rescan-icon.test.js`). Both pinned `.icon-shuffle` as the LAST
   member of the shared sizing / `@supports` selector lists, so adding any
   icon failed them on a correct change - the same over-specification
   `card-like.test.js` had already diagnosed and fixed for the fill guard in
   v1.47.6. They now assert MEMBERSHIP, and the loosening was
   mutation-verified (dropping `.icon-shuffle` from the group, dropping
   `.icon-flame` from the fill guard, and deleting `flame.svg` each still
   fail).
8. **The no-auto-run structural lock was updated, not bypassed**:
   `enumerateRepullableItems` moved from "exactly 1 call site" to "exactly 2",
   both named user-pressed routes, and `runSingleItemReheat`/`reheatOneItem`
   got their own exact-call-site locks plus membership in the auto-run
   allowlist sweep.

- Mutation-tested rather than asserted, across all rounds: the view-count

## What the gate caught

Recorded in full because the headline finding is the kind that invalidates a
"done" claim.

**Adversarial CRITICAL 1 - the relocation half was DEAD CODE.**
`planImportRelocation` skips with `recently-watched` for any file served
within `RECENT_STREAM_MS` (10 minutes). The watch page streams the video on
mount (`preload="metadata"`), which calls `markServed` on every serve, and the
watch page is this feature's ONLY entry point. So the proposal always came
back unavailable, and the confirm dialog, the `/relocate` route, the `newId`
navigation, the `archived:false` disclosure and the "Move it" wording were all
unreachable on a real install. Proven with a repro. The repo's own v1.41.6
test already asserted the behaviour that kills it.

Why 4949 green tests said otherwise: **every server test of the new route
stubbed `planImportRelocation`**, and there is no DOM harness for the client.
The feature's headline half never executed once in the suite. This is the
divergent-fixture class again, and the same shape as v1.47.4's dead headline
fix. Closed with tests that drive the REAL planner after a REAL stream.

**Adversarial CRITICAL 2** - `showConfirmModal` resolved its buttons with
`document.getElementById`, which returns the first match. Safe for four years
because every call site was synchronous from a click; the poll-driven
relocation offer is the first that can open one asynchronously. A reheat
completing while a DELETE confirmation was open re-labelled the delete
dialog's button to "Move it" and bound the relocate handler on top of the
delete handler - one click, both actions.

**Adversarial CRITICAL 3** - the confirm carried no binding to the proposal.
Re-running the decision proves a move is LEGAL, not that it is the move the
user APPROVED; subscribing to the channel from the page the reheat just fixed
up changes the destination folder.

**QA WARNING** - the relocate route checked the shared latch but never held
it, so "409 both ways" held in one direction only.

**QA WARNING** - the anti-drift characterization test this plan itself
specified under T1 was never written, and its absence was not disclosed.

**Adversarial CRITICAL 4 (delta round) - the fix for CRITICAL 3 was itself
dead code, in the same way.** The stale-proposal re-ask calls `offerRelocation`
recursively, which begins by refusing to open on top of an existing dialog.
`showConfirmModal` runs its teardown BEFORE `onConfirm`, and that teardown
leaves the backdrop in `document.body` for the ~200ms opacity transition - so
the bare `.modal-backdrop` query always matched the dialog that had just
triggered the re-ask, and the re-ask returned silently. It would have worked
only under `prefers-reduced-motion`. Fixed with
`.modal-backdrop:not(.modal-closing)`, plus a toast so a genuinely suppressed
offer is never dropped in silence.

**Adversarial WARNING 5 (delta round)** - the proposal binding bound the two
paths but NOT `transfer`, which is the safety sentence the dialog puts in
front of the user ("hard link, no data copied" vs "copied across filesystems,
original removed after a checksum match"). `classifyTransfer` measures the
device of the nearest EXISTING ancestor, because the channel dir usually does
not exist yet - so it can flip with both path strings byte-identical, and the
user consents to a hard link and gets a copy-then-delete. Now bound.

**Adversarial WARNING 6 (delta round)** - lifting `recently-watched` re-opened
the v1.41.10 DELETE_PENDING class. `moveItemToFolder` never called
`destroyMediaStreams`, unlike the delete route; the guard was incidentally the
only thing keeping a file this process was streaming out of that path, and the
new entry point makes the correlation certain. Now closed - which fixes the
Move button's identical, pre-existing exposure too.

## Honest gaps at ship time

- **Three of this wave's four CRITICALs lived in client code that only
  source-text regexes cover**, and CRITICAL 4 was the second one those regexes
  waved through. This repo's own v1.44 lesson applies directly: *a source-lock
  proves PRESENCE, not runtime BINDING*. One runtime test was added (driving
  the real `showConfirmModal` in a `vm` sandbox to prove the teardown-ordering
  property the CRITICAL 4 fix depends on), but the button mount, the poll, the
  toasts and the confirm flow remain presence-locked only.
- **The app was never run during this wave.** Every verification was tests plus
  static reasoning. CRITICAL 1 would have been visible in one manual click.
- **The flame glyph has never been rendered in a browser** (no SVG renderer in
  the environment; verified by rasterising the path to ASCII).
- The whole flow has never touched a real yt-dlp binary or real media.
- **The CRITICAL 4 runtime test proves ORDERING, not the timing margin.** Its
  sandbox stubs `setTimeout`, so the 300ms fallback never fires, and its fake
  `querySelector` ignores the `.modal-backdrop` class (it models only the
  `:not(.modal-closing)` half). The 200ms race itself is argued, not asserted -
  correctly, since it cannot be made deterministic. Revisit trigger: if the
  modal's transition duration or teardown ordering is ever changed.
- **`moveItemToFolder` releases one path where `DELETE` releases three.** The
  delete route also destroys streams on `transcodedPath(id)` and
  `audioPath(id)`; the move does not. Low risk (both live under `DATA_DIR`, so
  the SMB DELETE_PENDING trap does not apply and a POSIX rename over an open
  fd is fine), but the two functions now answer the same question differently.
  Recorded rather than fixed.
- **`POST /api/videos/:id/move` changed behaviour as a side effect.** An
  in-flight Range request on a file being moved now truncates mid-chunk
  instead of completing on its already-open fd. Judged correct (the client is
  about to hit a dead id regardless, and `DELETE` has made this exact trade
  since v1.41.10), but it is an unrequested change to a shipped route.

## Deferred, with revisit triggers

- **`showConfirmModal` has no backdrop-click or Escape handler.** Surfaced by
  the adversarial seat while tracing CRITICAL 2. Pre-existing, unrelated to
  this wave, and out of scope; worth doing when the modal is next touched.
- On the stale-proposal re-ask, the restored player pops its "Resume at X?"
  overlay and the confirm dialog then opens on top of it - two prompts for one
  failed action. Cosmetic; not worth a gate round.
- The playback restore fires unconditionally, so it can resume a player the
  user had themselves docked or closed before confirming. Capturing whether
  `close()` actually closed anything would make it symmetric.

## Risks to brief the adversarial seat on

1. The relocation is a real file move with no backup. Destroy the data:
   destination occupied, cross-filesystem copy interrupted, symlinked roots,
   NFC/NFD filename pairs, a concurrent scan, a concurrent delete of the same
   item, the id re-key racing the client's navigate.
2. The extraction in T1 is where a silent behaviour change hides. The
   persist-gate / stale-snapshot class has struck six times in this repo;
   a reheat landing mid-scan is exactly its habitat.
3. The view-count override (T2) must not leak into the batch.
4. The confirm dialog must not be able to describe a different destination
   than the executor uses (anti-drift), including when the db changes between
   the proposal and the confirm.
