## 1. Search box clears on a SUCCESSFUL search (Dean)

Friction: after a search, the query text stays in `#search-input`, so to search
again you must press the clear X first.

- Behaviour: after a search that returns >=1 result, clear the input text. On ZERO
  results, KEEP the text (so the X still resets it - Dean: "the X is useful when it
  didn't find what you wanted"). The results themselves ALWAYS stay - they are
  driven by the `?search=` URL param, not the input, so emptying the box never
  wipes results.
- Pure helper: `shouldClearSearchInputAfterResults(resultCount)` -> `count > 0`.
- Wire in main.js at the search-results render path, where the count is known.
  Must NOT re-trigger the "empty query -> reset to browse" logic.

## 2. Resume-countdown seconds field, 0 = instant (Dean)

The v1.132 resume prompt auto-fires after a hardcoded `RESUME_COUNTDOWN_SECONDS = 5`.
Add a configurable field beside the existing on/off toggle + resume/beginning action.

- New localStorage key `filetube_resume_countdown_seconds` (mirrors the existing
  resume-countdown keys; per-device, not per-account).
- Pure helper: `resolveResumeCountdownSeconds(raw)` -> integer clamp [0,30],
  default 5 on invalid/absent.
- 0 = fire the action IMMEDIATELY, no visible prompt/countdown ("instant resume").
- setup.html: numeric field + a one-line hint ("0 = resume instantly").
- Scope: RESUME prompt ONLY. Do NOT touch the autoplay-next countdown.

## 3. Delete button on video notifications (Dean) - DESTRUCTIVE

Notifications are `<a class="notif-row">` with a sibling `.notif-row-dismiss` X
inside `.notif-row-wrap`. Add a sibling trash button next to the dismiss.

- SIBLING of the anchor (never nested), so tapping it cannot navigate - the same
  isolation the dismiss X already uses. NO stopPropagation (v1.153 router scar).
- Two-tap arm via the pure `nextArmState` reducer (mirrors the card `.card-delete-btn`):
  first tap arms ("Sure?"), second tap deletes. Tapping the row (open) or the
  timeout disarms.
- Delete verb: `DELETE /api/videos/:mediaId` (SAME as a card -> Trash, recoverable).
  Report via `deleteResultToast`.
- NON-OPTIMISTIC (v1.54 law): row leaves only on a confirmed 2xx; failure re-enables.
  On success remove the row + refresh the badge (mirrors dismiss).
- MEDIA rows only (`kind === 'media'` with a real `mediaId`). Podcast/system rows
  keep only the dismiss X.
- RE-RENDER SAFETY (v1.159 Trash-arm bug): armed state stays LOCAL to the button so
  a notification refresh rebuilds it idle - an armed one-tap must never survive a
  poll. Adversarial seat briefed to try exactly this.

## 4. Video background-play resets 1.5x -> 1x (Dean device bug)

Repro: play a video at 1.5x, background it -> background AUDIO plays at 1x. Audio-only
is NOT affected. On FOREGROUND the video is instantly 1.5x again.

- Diagnosis (evidence, not theory): the video element KEEPS 1.5x (correct on return),
  so it is the background-audio HANDOFF that runs at 1x. Audio-only never hands off,
  so it is immune. player.js:5199-5215 already warns a media load() resets
  playbackRate to defaultPlaybackRate and that the code deliberately avoids
  defaultPlaybackRate - READ WHY before touching it.
- Fix direction (to confirm against the actual handler): copy the live
  `mediaPlayer.playbackRate` onto the background-audio element at handoff, and keep
  it synced if the rate changes during background. Do NOT rebuild the battle-won
  bg-audio machinery (memory law) - reuse it.
- FALSIFIER: if the background path does NOT use a separate audio element/handoff,
  this theory is wrong - re-root-cause.
