## The problem (on-device evidence, 2026-07-25)

Some files that play everywhere else fail on Roku with "malformed data":

- **Confirmed root cause #1 — embedded cover-art track.** Dean's failing file
  (`/media/ytdlp/planetclue/finding GOLD in the Wii Shop Channel
  [l5ECEYybuBo].mp4`) ffprobes as TWO video streams: `h264 / High / yuv420p /
  level 42` (fully Roku-compatible) **plus `png / rgb24`** — a yt-dlp
  `--embed-thumbnail` attached-picture track. Browsers/phones skip it; Roku's
  MP4 demuxer aborts. This is a *class*: potentially every yt-dlp download
  with an embedded thumbnail.
- **Confirmed root cause #2 — rotation metadata.** Phone recordings carry a
  rotation display-matrix; Roku's Video node ignores it (browsers honor it),
  so those videos play sideways on the TV.
- (10-bit H.264 was suspected but is NOT confirmed in Dean's library; cover
  the detection cheaply if free, don't build for it.)

## Dean's hard constraint (his words: "only apply on the TV app")

**Zero file mutation. Zero library-wide processing.** Renditions are
on-request, cache-only, served exclusively to clients that ask. Web player,
downloads (`?download=1` stays byte-identical), backups: untouched and
unaware. Deleting the cache (or the channel) leaves no trace in the library.

## Design sketch (settle at intake; recommendations inline)

- **Trigger:** Roku channel requests `GET /video/:id?compat=roku` (one-line
  channel change on `feature/roku-channel` or a follow-up commit). Without
  the param, behavior is exactly today's.
- **Verdict:** on first `compat=roku` request for an item, ffprobe the source
  (streams + side_data rotation), cache a per-id verdict:
  - `clean` → serve the original (today's `sendRangeable` path).
  - `strip` (extra attached-pic/image video stream) → **remux**: stream-copy
    minus image tracks, `-movflags +faststart`. Seconds per file, lossless.
  - `rotate` (display-matrix present) → re-encode via the EXISTING transcode
    pipeline (ffmpeg autorotates on re-encode). Reuse its 503
    `{error:"transcoding"}` contract — the channel already handles it.
  - Recommendation: lazy per-request probing over scan-schema changes; no
    backfill pass needed, nothing touches items the TV never plays.
- **Cache:** renditions + verdicts keyed by id + source (size, mtime) so a
  replaced file invalidates. Live in the existing transcode-cache area.
  **MUST be outside every library root** (the scan must never discover a
  rendition as media — v1.41.6 seam-class risk). Eviction: follow whatever
  tts-cache (tech-debt #37) decided, or add a twin tech-debt entry.
- **Also in scope (small):** `Cache-Control` on `/thumbnail/:id` (currently
  bare `res.sendFile`) — Dean reported slow grid thumbnails.
- **Out of scope:** transcoding for codec taste (brief's non-goal), music
  library on Roku, chapters overlay, PIN pairing, progress write-back
  (candidate v2 channel features, separately).

## Verification requirements

- Fixtures: canned ffprobe JSON for the decision function (CI has no ffmpeg —
  stub-ffmpeg harness per v1.33); divergent fixtures (attached-pic mp4,
  rotated mov, clean mp4, multi-audio mkv) — the v1.41.9 lesson: fixtures
  must diverge where reality does.
- Range requests must work against renditions (Roku seek/resume).
- Prove `?download=1` and the plain `/video/:id` path byte-identical before
  and after (the no-mutation contract).
- **Full two-reviewer gate** (server change). Brief the adversarial seat on:
  cache poisoning/staleness (source replaced, same id), the scan-vs-cache-dir
  seam, concurrent first-requests racing the remux, and disk exhaustion.
  Dual-Node suites, standard ceremony.
