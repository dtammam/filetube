# v1.96.0 — Watch action bar: shorter buttons + kill the load flash

Status: ACTIVE. Branch `release/v1.96.0`. Wave A of the two-wave mobile batch
(Wave B = "Hide from feed", separate release).

## Problem (Dean, on-device)

v1.95 added a mobile 44px touch floor via `.btn { min-height: var(--size-touch) }`
in the EOF `@media (max-width:768px)` block. On the WATCH page that made the
`.watch-actions` action-row buttons (Queue/Next/Download/Delete + JS-injected
Move/Attribute/Like/Watched/Share/Reheat) too tall. Separately, that row
FLASHES on load: watch.html ships 4 static buttons, then watch.js injects the
rest AFTER the `/api/videos/:id` record resolves, so the row renders
partial -> full (a two-render reflow / pop-in).

## Task A1 — 5px shorter, scoped

On mobile, the watch action-row buttons only drop to **39px** (5px under the 44
floor, still above the ~36px pre-v1.95 height). Scoped to `.watch-actions .btn`
so the v1.95 queue / notification / resume 44px controls and every other `.btn`
are untouched. 39px is Dean's starting number and his device pass is the
arbiter, so it is a single tunable token `--size-touch-watch-action: 39px`
(defined beside `--size-touch`). height/min-* are NOT census-governed.

- Wins over the v1.95 EOF `.btn { min-height:44px }` by SPECIFICITY
  (`.watch-actions .btn` = 0,2,0 > `.btn` = 0,1,0), so cascade order is
  irrelevant — but the rule still ships in a NEW `@media (max-width:768px)`
  block APPENDED at EOF (positional-test safety; v1.95 lesson).
- The playlist / prev-next buttons live OUTSIDE `.watch-actions`, so they keep
  the 44px floor (Dean: "leave the playlist button").

## Task A2 — reveal-once, no pop-in

Reveal the WHOLE action row ONCE in its final state (Dean's decision:
whole-row shimmer then reveal; buttons may be briefly non-tappable during the
short record load — do NOT decorate the half-state).

Mechanism:
- watch.html: `.watch-actions` ships a `data-loading` ATTRIBUTE (NOT a second
  class — the `class="watch-actions"` substring is locked by
  watch-action-bar-nowrap.test.js's `indexOf`, and several tests extract the
  base rule via `/\.watch-actions\s*\{/`, which an attribute selector does not
  disturb).
- CSS `.watch-actions[data-loading]`: `--bg-secondary` fill + the shared
  `@keyframes skeleton-sweep` ::after (same treatment `#views-count` already
  uses right above), and `> * { visibility: hidden }` so every child (stars +
  all buttons) is invisible-but-laid-out while loading.
- watch.js: the row's final button set depends on TWO async inputs — the media
  record (`/api/videos/:id`) AND the write capability (`fetchCurrentUser()` /
  `/api/auth/me`). Move + Attribute are gated on `canModifyLibrary` and mount
  from WHICHEVER of {media, capability} resolves LAST. So the reveal is
  BARRIERED: `maybeRevealActionBar()` drops `data-loading` only when BOTH
  `actionMediaSettled` AND `actionCapabilitySettled` are true. Media releases in
  the hydration success tail AND the `catch` (no mediaData → Move/Attribute
  never mount → static set is final); capability releases in `fetchCurrentUser`'s
  `.then` and `.catch` and the no-`fetchCurrentUser` `else`. The early
  player-slot-missing bail-out also reveals directly (initWatch never runs there).

At the reveal instant every child is already in the DOM and laid out (just
invisible), so the reveal itself is ZERO-SHIFT. It is not an absolute no-resize:
the shimmer box occupies the 4 static buttons' height (~1 row on mobile) during
the record fetch, then SETTLES to its final height as the injected buttons mount
invisibly — a single placeholder resize under the uniform shimmer, NOT the
button-by-button pop-in this fix targets. A fixed final height cannot be reserved
(the count is data-dependent), so a browser-measured settle is the honest floor.

`fetchCurrentUser()` is memoized module-wide and the shell kicks it off at boot,
so in practice the capability side is already settled when watch init runs — the
barrier adds negligible delay while closing the cold-load race.

### Known residual (DISCLOSED)

The Reheat button mounts OPTIMISTICALLY from the v1.53 capability cache on a
warm cache (the common repeat-visit case — in the row before reveal). On a
COLD cache (first tab session only), it mounts ~1 RTT later, after
`probeReheatModule()` resolves, i.e. after reveal — the SOLE late-mount not
covered by the barrier, unchanged from today and already minimized by the
capability cache. Blocking the whole row's reveal on that network probe would
keep the common buttons (Download/Delete/Queue) non-tappable for an unbounded
time, which is worse. Accepted; revisit trigger = Dean reports a first-session
reheat pop-in. (The gate's first pass caught that Move/Attribute shared this
exposure via the independent capability promise — now FIXED by the barrier, not
merely disclosed.)

## Tests (predictions the suite re-verifies)

- A1: a NEW EOF `@media (max-width:768px)` block sets `.watch-actions .btn`
  `min-height: var(--size-touch-watch-action)`; the token resolves to 39px and
  is `< --size-touch` (44px). Global `.btn` keeps the 44px floor. The new token
  completes the three-place ceremony (CONTRIBUTING:66): `:root` +
  `token-scale-lock.test.js` CONTRACT (count 48→49) + the contract doc.
- A2 source (test/unit/watch-action-bar-reveal.test.js): `.watch-actions` ships
  `data-loading`; `> * { visibility: hidden }` + shimmer; `revealActionBar()`
  removes the attribute; `maybeRevealActionBar()` is gated on
  `actionMediaSettled && actionCapabilitySettled`; the media side releases twice
  (success + catch), the capability side thrice (then + catch + no-probe else).
- A2 behaviour (test/integration/watch-action-reveal.test.js — the BINDING):
  boots real watch.html under jsdom and drives resolution order of
  `/api/videos/:id` vs `/api/auth/me`. Asserts the row stays `data-loading`
  until BOTH settle (media-first and capability-first orderings), reveals with
  Move present for an admin, reveals a strictly-complete row (no Move) for a
  read-only user, and reveals on a 404 (catch). MUTATION-VERIFIED: a
  reveal-on-media-alone regression turns tests 1–2 RED.

## Non-goals

Cards, preview clips, and `#views-count` already reveal-once — do not
re-scope them. Fix the action bar only; leave a one-line note to reuse the
`data-loading` pattern if another half-state shows up.

## Adversarial attack surfaces (brief)

- Prove the reveal-once still flashes/clips the row on some record shape
  (read-only user with fewer buttons; audio vs video; seeded vs cold load;
  error path).
- Prove it reintroduces the iOS `.watch-actions` shrink-to-fit / nowrap
  regression (v1.25.5) or an on-reveal layout JUMP (reserved height != revealed
  height).
- Prove the 39px rule leaks onto a non-watch `.btn`, or that the queue/notif/
  resume 44px controls regressed.
