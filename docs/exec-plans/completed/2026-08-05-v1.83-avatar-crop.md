# v1.83.0 - Avatar crop (pick any photo, pan + zoom a circle)

Status: SHIPPED v1.83.0 (docs reset 2026-08-15; see ROADMAP.md). Was: ACTIVE - Dean's device-pass wish after v1.82 shipped ("wishing I could
use a larger than 1MB image and then crop / pick a section"). Intake settled:
circular pan-and-zoom cropper, BUILT in-house (no dependency).

## Framing (the unifying insight, agreed at intake)

The two wishes are ONE feature. A client-side crop that DOWNSCALES the selected
region before upload means the source image size stops mattering: pick any huge
phone photo, crop it, and the uploaded avatar is always small. So the server cap
stays (a 400px JPEG is tens of KB, far under 1 MB) and no server change is needed
beyond leaving the existing magic-byte/allowlist route exactly as-is - the canvas
export is a real PNG/JPEG/WebP that passes the sniff.

## The shape

When a user picks a file at EITHER entry point (the account menu's "Change photo"
and Settings->Account "Upload"), instead of uploading the raw file we open a crop
modal, and only the cropped+downscaled Blob is uploaded. One shared implementation
drives both call-sites (the v1.41.4 one-writer discipline).

## Locked decisions (Dean)

- **Circular pan + zoom** (Google/YouTube style): the image sits under a fixed
  circular frame; drag to pan, wheel/pinch to zoom; Save/Cancel.
- **Built in-house**, no vendored lib, no new dependency; token-styled modal.
- Output: a square canvas (the circle's bounding box) at a fixed size; the avatar
  CSS already masks it to a circle on display, so we export the square.

## Architect decisions (flag for Dean)

1. **Output 400x400, JPEG q~0.9** (with a PNG fallback if the source had alpha is
   NOT needed - avatars are opaque circles; JPEG is smallest). A 400px avatar is
   crisp at every render size we use (32/44px + any future 2x). Result ~30-80 KB.
2. **Cover constraint**: the image must always fill the circle (no empty gaps);
   min-zoom = circle-diameter / min(imageW, imageH) at display scale, and pan is
   clamped so an edge can never cross into the circle.
3. **No server change**: `AVATAR_MAX_BYTES` stays 1 MB (the cropped output is far
   under it). The route is untouched.

## Task breakdown

- **T1 - the pure crop geometry (testable, no DOM).** `lib`-style pure functions
  (exported from common.js for node:test, like the bottom-nav resolver):
  - `avatarMinScale(imgW, imgH, circleD)` - the cover minimum.
  - `clampAvatarOffset(offset, scale, imgW, imgH, viewport, circleD)` - keep the
    circle fully covered.
  - `avatarSourceRect(scale, offset, viewport, circleD)` - the source-image
    rectangle currently under the circle's bounding box (what drawImage copies).
  Unit-tested: min-scale for portrait/landscape/square, clamp at each edge,
  source-rect round-trips a known pan/zoom.
- **T2 - the crop modal + gestures (common.js).** `cropAvatarFile(file)` returns
  `Promise<Blob|null>` (null = cancelled). Loads the file into an Image
  (URL.createObjectURL, revoked after), renders it in a viewport with a circular
  mask, wires pointer pan + wheel zoom + touch pinch, a zoom slider, Save/Cancel.
  On Save: draw the source rect (T1) into a 400x400 offscreen canvas, `toBlob`
  JPEG, resolve. Escape/backdrop = Cancel. Focus-trapped; token-styled.
- **T3 - wire both entry points.** The menu (common.js ~5026) and Settings
  (setup.js ~1797) `change` handlers call `cropAvatarFile(file)` first; upload
  the returned Blob (Content-Type from the Blob) only if non-null. Honest errors
  unchanged. A browser without canvas/toBlob falls back to uploading the raw file
  (feature-detect; the server cap then applies as before - disclosed).

## Acceptance criteria

- **AC1** Picking a large (>1 MB) source photo works: the crop modal opens, and
  the uploaded avatar is a small (<200 KB) 400x400 image - the source size never
  hits the server cap.
- **AC2** Pan + zoom stay within the cover constraint (no gap ever shows inside
  the circle); Save produces the region under the circle; Cancel uploads nothing.
- **AC3** Both entry points (menu + Settings) route through the SAME
  `cropAvatarFile`; neither uploads a raw file on the happy path.
- **AC4** The pure geometry is unit-bound (min-scale, clamp, source-rect).
- **AC5** Design-token census stays 0; no new dependency; server route unchanged.
- **AC6** Graceful fallback when canvas/toBlob is unavailable (raw upload, cap
  applies) - no crash.

## Named attack surfaces (for the gate)

- S1 the cover/clamp math: a pan/zoom that leaves a gap inside the circle, or a
  source-rect that reads outside the image bounds (drawImage of a negative/oob
  rect). Portrait vs landscape vs tiny (< circle) source.
- S2 the Blob: is the exported type in the server allowlist (JPEG)? Does a huge
  source (e.g. 8000x6000) still export a small 400px Blob (memory/size)? An
  animated GIF / SVG picked (server already rejects non-allowlisted; the client
  canvas flattens or fails gracefully).
- S3 lifecycle: object URL revoked (no leak); modal single-instance; Cancel/Escape
  path uploads nothing and restores focus; the file input re-picks the same file.
- S4 both call-sites truly share the one function (grep - no raw-file upload left
  on a happy path).
