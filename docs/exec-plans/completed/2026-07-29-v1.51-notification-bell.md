# v1.51.0 - Notification bell (new-download notifications)

Status: SHIPPED v1.51.0 (docs reset 2026-08-15; see ROADMAP.md). Was: ACTIVE. Owner: main session (lean mode). This document is the
reviewers' spec for the two-reviewer gate.

## What Dean asked for (2026-07-29, verbatim intent)

A YouTube-like notification bell, top-right corner, showing the number of
not-yet-seen downloaded videos. Tapping it shows a chronological list of
downloads - icon, channel, time, name - "basically the exact real
experience on desktop/mobile". Clearable, server-side cleared. Tapping an
entry navigates to the item and un-news it. Enabled with the ytdlp
integration explicitly / when someone has at least one sub. Bonus points
if the shape could later feed real desktop/mobile push notifications.
Plus (follow-up message): an explicit instance-wide settings toggle.

## Decisions (all probed with Dean, all AGREED)

| # | Decision |
| - | -------- |
| 1 | Notification source: EVERY yt-dlp download - subscription polls AND one-off/universal, video and audio. Hand-dropped files, reheats, re-inits never notify. |
| 2 | ONE global event feed; PER-USER unread/cleared state (YouTube-per-account). |
| 3 | Two-tier YouTube semantics: opening the panel zeroes the NUMBER badge (mark-seen); each row keeps a "new" dot until tapped (mark-read); "Clear all" empties the panel. All server-persisted. |
| 4 | Day one after upgrade: seed the ~30 most recent yt-dlp-provenance items as ALREADY-READ history (panel populated, badge 0, no dots). |
| 5 | Deleted media: prune its notifications server-side (no tap-to-404). |
| 6 | Mobile: bell stays top-right in the header; panel becomes a full-width sheet. |
| 7 | Real push is a FOLLOW-UP wave (Dean confirmed HTTPS, so Web Push is viable later; VAPID via node:crypto keeps the no-new-server-deps rule). This wave only shapes the feed so push can bolt on (monotonic ids, server-side generation point). |
| 8 | Instance-wide settings toggle, default ON, in the settings menu. When OFF: bell hidden, endpoints answer disabled, feed still ACCUMULATES (no history gap on re-enable). |
| 9 | Visibility rule: ytdlp module enabled AND >= 1 subscription AND toggle on. |

## Architecture

### Storage (SQLite migration v4 -> v5, lib/db/sqlite.js)

Forward-only migration block, `SCHEMA_VERSION` 4 -> 5 (doctrine at
lib/db/sqlite.js:171-180). Three relational tables (NOT doc_kv - this is
per-user relational state, the v1.43+ pattern):

- `notifications(id INTEGER PRIMARY KEY AUTOINCREMENT, media_id TEXT NOT NULL UNIQUE, created_at INTEGER NOT NULL)`
  - Global feed. `media_id` UNIQUE: a re-download of the same path
    replaces the old row (delete-then-insert so the row gets a fresh id
    and re-sorts to top; orphaned reads for the old id are deleted in the
    same transaction).
  - Display fields (title, channel, avatar, thumbnail, type) are JOINED
    from `db.metadata` at read time, never denormalized - the item is
    the source of truth and prune-on-delete (decision 5) guarantees the
    join target exists.
  - Cap: newest 200 rows; overflow deleted oldest-first (with their
    reads) on insert.
- `user_notification_state(user_id INTEGER PRIMARY KEY, last_seen_at INTEGER NOT NULL DEFAULT 0, cleared_at INTEGER NOT NULL DEFAULT 0)`
- `user_notification_reads(user_id INTEGER NOT NULL, notification_id INTEGER NOT NULL, read_at INTEGER NOT NULL, PRIMARY KEY(user_id, notification_id))`

Semantics (all times epoch ms, all filtering server-side):

- Panel list: rows where `created_at > cleared_at(user)`, newest first.
- Badge (unseen) count: rows where `created_at > max(last_seen_at, cleared_at)`.
- Row dot (unread): no `user_notification_reads` row for (user, id).
- Open panel -> mark-seen (`last_seen_at = now`). Tap row -> mark-read.
  Clear all -> `cleared_at = now` AND `last_seen_at = now`.
- A user with NO state row defaults `last_seen_at` to their account
  `created_at` (users table) - a brand-new user does not get a badge
  full of downloads that predate their account. `cleared_at` defaults 0.

Accessors live in **lib/auth/store.js** (`createUserStore`) - it already
owns every relational table and, critically, the id-keyed-carrier
lifecycle seam: `removeMediaState` and `rekeyMediaState`
(lib/auth/store.js:323/:340) MUST gain the notifications tables in the
same transaction (this bug class is on its seventh strike per the
comment at lib/auth/store.js:59-62). New methods:

- `recordNotifications([{mediaId, createdAt}])` (insert + cap + replace semantics)
- `listNotifications(userId)` -> rows + per-row unread flag
- `countUnseenNotifications(userId)`
- `markNotificationsSeen(userId, nowMs)` / `markNotificationRead(userId, id, nowMs)` / `clearNotifications(userId, nowMs)`
- `countNotifications()` (seeding guard)
- `removeMediaState`/`rekeyMediaState` extended (delete/rekey feed rows + reads)

### Generation (server.js scan, Phase-2)

The three downloadMeta consume sites (server.js ~4409/4444/4487) are the
hook - they fire only for freshly-indexed files under the yt-dlp
download roots (guard at server.js:4383), and the bridge entry is
deleted on first consume, so reheats/re-encodes/hand-drops physically
cannot notify (decision 1 falls out of the existing structure).

ONE shared collector (v1.41.4 lesson) called from ALL THREE sites inside
the mutator: pushes `{mediaId: item.id, createdAt: item.addedAt}` (file
birthtime == download completion; fallback `Date.now()`) onto a
scan-local `pendingNotifications` array. The actual SQLite insert
happens POST-COMMIT via `userStore.recordNotifications(...)`, the exact
posture the per-user prune already uses (server.js:4612-4618) - never
an await inside the synchronous mutator. If the mutator bails (stale
epoch), nothing was collected/committed, nothing is inserted.

Generation is NOT gated on the settings toggle or sub count (decision 8:
feed accumulates while hidden). It IS inherently gated on the ytdlp
module being enabled (no downloads happen otherwise).

### Endpoints (server.js core, after the auth gate - auth is free)

Gate helper `notificationsFeatureEnabled(db)` = ytdlp `isEnabled(config)`
AND `db.ytdlp.subscriptions.length >= 1` AND
`db.settings.notificationsEnabled !== false`. Disabled -> 404
`{error: 'notifications disabled'}` (the 2xx-probe convention).

- `GET /api/notifications` -> `{items: [{id, mediaId, createdAt, title, channelName, channelAvatarUrl, hasThumbnail, type, unread}], unseenCount}` (joined from metadata; a row whose item vanished mid-flight is filtered defensively - prune-on-delete is the real mechanism)
- `GET /api/notifications/badge` -> `{count}` (doubles as the client's boot probe)
- `POST /api/notifications/seen` -> `{success: true}`
- `POST /api/notifications/read` `{id}` -> `{success: true}` (400 on bad id)
- `POST /api/notifications/clear` -> `{success: true}`

Settings: `notificationsEnabled` (boolean) joins the validated settings
keys (server.js ~4996 "unknown setting" check) + a toggle in setup.html's
settings UI following the existing toggle pattern.

### Seeding (decision 4)

At server boot, once: if `countNotifications() === 0` AND
`db.settings.notificationsSeededAt` absent -> take the 30 most recent
`db.metadata` items with yt-dlp provenance (youtubeId OR
sourceExtractor OR channelUrl), insert with `created_at = addedAt`,
insert read rows for every existing user, set every existing user's
`last_seen_at = now`, then persist `notificationsSeededAt` via
`updateDatabase`. Idempotent by the flag; a genuinely empty library
still sets the flag (nothing to seed twice later - post-flag downloads
notify normally).

### Client (public/js/common.js - zero per-shell markup edits)

New boot injector `injectNotificationBellIfEnabled()` in the
DOMContentLoaded shell boot (common.js ~7630 region, once per real page
load; header lives outside #view-root so SPA swaps never touch it).
Probe = first `GET /api/notifications/badge`; non-ok -> inject nothing,
no poll (fail closed, the subscriptions-nav posture).

- Bell button (createElement/textContent ONLY - the shell-chrome
  convention) appended into `.header-right` on all 8 headered shells;
  login/welcome have no header and are pre-auth anyway.
- Badge bubble: red count chip on the bell (precedent:
  `.dl-status-chip-dot` styling family); hidden at 0.
- Poll: recursive `setTimeout`, 60s cadence, skip while
  `document.hidden`, resume on `visibilitychange`/`pageshow` (the
  download-chip pattern, common.js:7283).
- Panel: own CSS classes (v1.50.3 lesson: never share a sibling popup's
  class expecting its JS behavior). Desktop: right-anchored dropdown
  under the bell (inside header's z-index:1000 context). Mobile
  (<=768px): full-width bottom-sheet layout (styled like the playlists
  sheet, own classes). Uses `openOverlay`/`closeOverlayThen` helpers.
- Dismissal: outside-click via `click` + `pointerdown` + `touchstart`
  (iOS lesson, player.js:4652-4658), Escape via capture-phase keydown
  (shortcuts-modal precedent), and close-on-row-navigation. The bell is
  shell-level chrome, so the player's dock() dismissal pair is NOT
  implicated - but the gate should verify no player-slot interaction.
- Open panel: fetch list, render, POST seen, zero the badge locally.
- Row: avatar (resolveAvatarSource + a small common.js DOM applier -
  watch.js's applyAvatarToElement is closure-local there), channel name,
  title, thumbnail (`/thumbnail/<id>` when hasThumbnail), relative time
  (formatRelativeTime, epoch ms), unread dot. Row is a real
  `<a href="/watch.html?v=<id>">` so the global anchor handler SPA-routes
  it for free (video AND audio items both live on watch.html).
- Tap row: POST read (fire-and-forget with keepalive), drop the dot,
  close panel, let the anchor navigate.
- Clear all: panel-header button -> POST clear -> empty panel + badge 0.
- MOBILE HEADER FACT: `.header-right { display: none }` at <=768px
  (style.css:3682). The bell gets a deliberate mobile rule: header-right
  becomes visible again as an absolutely-positioned top-right block
  containing ONLY the bell (Settings btn already display:none on mobile;
  theme toggle gets the same). Flagged as a DEVICE PROBE (CSS-blind
  gate lesson - device is the layout gate).

### Push-readiness (decision 7, this wave's only obligation)

Monotonic AUTOINCREMENT ids + a single server-side generation point
(`recordNotifications`) = a future push wave subscribes at that point
and delivers rows > last-pushed-id. Nothing else ships now.

## Gate round 1 (both seats REQUEST CHANGES; every finding applied)

- QA W1 (restore state-loss): a feed-only bundle (notifications without a
  users array) destroyed every existing user's read markers.
  `replaceAllNotificationsRaw` now snapshots reads by MEDIA id pre-wipe and
  re-resolves them post-insert; a users-carrying restore still supersedes
  wholesale. HTTP-level test added.
- QA W2 (promised tests missing): reheat-produces-no-row now proven against
  the PRODUCTION writer (`recordRepulledItemMeta`, repull-persist suite);
  move-re-keys-the-feed now proven through the real `POST /:id/move`
  endpoint (move-files suite).
- QA S1 / adversarial W2 (re-key collision orphans reads): `rekeyMediaState`
  scrubs a colliding destination row (reads first) before the re-key; the
  inaccurate "only the feed row moves" comment fixed; unit test added.
- Adversarial W1 (REPRO'D — birthtime is the wrong clock): live
  notifications are now stamped with the CONSUME moment, never
  `item.addedAt` (yt-dlp's .part-rename makes birthtime the download START;
  NAS clock skew makes it un-zero-able). Seeding still uses addedAt (rows
  born read+seen; only ordering matters there). DESIGN CHANGE from the
  original plan text ("createdAt = addedAt"), reviewer-prescribed.
- Adversarial W3 (badge/panel disagreement): the panel's join net now
  PRUNES phantom rows (via `removeMediaState`, the one deleter) so the
  badge re-agrees after first open; `replaceAllNotificationsRaw` enforces
  the 200 cap on restored feeds. Residual: a badge may over-count phantoms
  until the panel is first opened or the next scan prunes — accepted,
  disclosed below.
- Adversarial S1: bundle validation now field-checks notification entries
  (shape, positive createdAt, duplicate mediaId) → clean 400 before the
  wipe, matching the refuse-whole posture.
- Adversarial S2: rows that predate a user's ACCOUNT never wear dots (a
  post-seeding account no longer opens to 30 dotted history rows). Applied
  as a general rule in `listNotifications`.

## Gate round 2 (delta re-confirms)

Both seats APPROVED the round-1 delta (QA: no new findings; adversarial:
two new NON-BLOCKING findings, both applied same-day per the
apply-when-cheap norm):

- Adversarial residual WARNING (repro'd): seeding still trusted a FUTURE
  addedAt (rsync -t clock skew on a btime-less filesystem) -> day-one badge
  that mark-seen could not zero. Fixed: `Math.min(addedAt, nowMs)` clamp at
  the seeding boundary; bridge-suite test seeds a +6h file clock and
  asserts badge 0 with a clamped row.
- Adversarial SUGGESTION: the panel join read `metadata[mediaId]` with a
  plain lookup, so a crafted admin bundle seeding `mediaId: 'constructor'`
  rendered an inherited junk row the phantom-prune skipped forever. Fixed:
  own-property lookup (the v1.42 __proto__ row-key lesson); prototype-key
  rows now read absent and prune like any phantom. API-suite test locks it.

## Known gaps / accepted residuals (disclosed up front)

- Music-namespace tracks (db.music.tracks) never notify - the feed
  covers the main media library (video+audio) where yt-dlp downloads
  land. Revisit if Dean routes yt-dlp audio into music folders.
- The badge is poll-based (<=60s latency), not push - push is the
  follow-up wave.
- Bell hidden until the FIRST subscription exists even if one-off
  downloads occur (decision 9, Dean's spec).
- (Gate round 1) The badge counts feed rows without a metadata join, so a
  phantom row (item deleted while its removeMediaState call failed, or a
  restored feed naming since-deleted media) can transiently over-count
  until the panel is first opened (which prunes it) or the next scan
  prune runs. Self-healing, bounded, accepted.
