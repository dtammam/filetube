## The ask, verbatim intent

Dean: awareness of something playing for a user on another device, allowing
handoff or continuation. NOT direct control of the other device. State-aware
play so he can pick up on the PC what was playing on the iPhone (and vice
versa). "YouTube has something similar - I want that."

## Framing (agreed at intake)

Most of "pick up where I left off" already exists and this wave must NOT
rebuild it:

- Position is already near-live server-side: the shared player POSTs a
  progress ping every ~4s while playing; the write coalescer plus
  `effectiveProgress` (server.js ~line 872) means any reader sees a
  position at most a few seconds stale.
- The queue is already ONE server-side per-user queue (v1.71,
  `lib/queue/store.js`); continuation inherits queue context for free.
- Music has its own resume pointer (`/api/music/resume`).

What is genuinely missing, and the ENTIRE scope of this wave:

1. **Device identity** - sessions bind `{uid, tv}` only; no per-device id,
   no human-readable device name.
2. **Activeness** - a presence concept: "is playing RIGHT NOW on the
   iPhone" vs history's "was played at some point."
3. **The discovery affordance** - a YouTube-style toast card offering
   continuation at the moment the user sits down at another device.

Shape: a device-tagged presence layer piggybacked on the existing progress
pings, one read endpoint, one toast card. No sync plumbing, no remote
control, no schema migration expected.

## Intake rulings (numbered; Dean's replies in parentheses)

1. **Kinds in scope** (agree): the three player-carried kinds - video,
   podcast episodes, music tracks. Books/reading OUT (different resume
   model, not "playing"). Roku OUT for v1 unless the implementer verifies
   its client already sends progress pings AND inclusion is near-free;
   otherwise disclose as out of scope.
2. **Affordance** (perfect): dismissible toast card on Home and other
   top-level list surfaces. Click navigates to the normal watch/listen
   surface; dismiss hides for that item+device until the state changes.
   Nothing shown on a surface that is itself mid-playback of that item.
3. **Device identity + naming** (like it): per-device UUID minted
   client-side (localStorage) + auto label derived from UA ("iPhone",
   "iPad", "PC", "Mac", "Android"...). Settings rename DEFERRED to a
   follow-up if auto labels read well - do not build rename in this wave.
4. **Transport** (cool): piggyback `deviceId`/`deviceLabel` on the
   existing ~4s progress pings - zero new write cadence - plus one new
   read endpoint. Poll on page load + light visible-tab interval (~30s),
   paused while the tab is hidden. NO SSE/WebSocket.
5. **Liveness + persistence** (cool): in-memory only, no DB change,
   cleared on server restart (degrades gracefully to plain history
   resume). "Active/playing" = ping within ~15s. After pings stop, the
   entry lingers as "paused" for ~30 minutes, then expires. An EXPLICIT
   pause beacon flips the state immediately (see design); ping cessation
   without a beacon (app killed) degrades to paused after the active TTL.
6. **Read-only pickup** (got it): no message to the origin device, no
   auto-pause there. Known residual TO DISCLOSE in release notes: two
   devices playing the SAME item fight over progress last-writer-wins
   every ~4s. True today already; handoff makes it easier to trigger.
   Accept, disclose, do not solve.
7. **Multiple other devices active** (taken as agreed by silence -
   re-confirm if convenient): surface only the MOST RECENT other-device
   presence. No device list.

## UI spec (Dean approved this specific visualization: "I want that")

The YouTube desktop "Continue watching?" bottom-corner toast, merged with
YT Music's "Playing on <device>" pill: the card, but the headline names
the DEVICE, because the device is the news.

Mounted in the PERSISTENT SHELL - never inside `#view-root` (the v1.38
SPA-swap bug class: works on refresh, dies on in-app nav). Bottom-left on
desktop; above the bottom bar on mobile.

```
+-------------------------------------------+
| * Playing on iPhone                    x  |
| +----------+  Woodturning a Bowl, Pt. 2   |
| |  thumb   |  12:34 / 45:06               |
| | ######.. |  [ > Continue here ]         |
| +----------+                              |
+-------------------------------------------+
   ###### = red/accent progress bar along the
   thumbnail's bottom edge (YouTube signature)
```

Two states, same card:

- **Live:** `* Playing on iPhone` (accent-colored dot) - timestamp
  advances as polls land.
- **Lingering:** `|| Paused on iPhone - 18 min ago` - shown for the
  30-minute linger window (the sit-down-at-the-PC case).

Rules:

- All styling via design tokens; every one of the four era skins must be
  covered (the token census + ratchet enforce this; remember the census
  is selector-blind to `[data-theme]`-scoped consumer rules - residual
  #103 - so the QA seat verifies skins by eye/DOM, not census-green).
- Glyphs come from CSS/the glyph pool, never emoji codepoints in markup.
- The card never shows the CURRENT device's own presence to itself
  (deviceId equality check).
- Click "Continue here": navigate to the kind-correct surface (video ->
  watch page, podcast episode -> its play surface, track -> music
  surface). The card does NOT carry the resume position for playback -
  the destination surface already resumes via `effectiveProgress` /
  music resume, which is near-live. The card's timestamp is display-only.
- Dismiss (x): suppress for that (mediaId, deviceId) pairing until the
  presence changes to a different item or flips state
  generation; per-tab/session persistence is fine (sessionStorage).

## Design sketch (for the implementer to verify and refine, not gospel)

### Client

- Device identity module (common.js or small new file): mint UUID once
  into localStorage (`ft_device_id` or similar), derive label from UA at
  startup. Both attach to every progress ping body.
- THE one shared write site is `public/js/player.js` ~line 3459-3460 -
  all three kinds funnel through it with per-kind `progressEndpoint`
  overrides (`music.js:636`, `podcasts.js:602`). Piggyback lands there
  ONCE. Machine-verify this claim at implementation time (grep for other
  progress POSTers; the "seat that forgot to call the shared helper" bug
  class applies in reverse - a writer that BYPASSES the shared site would
  silently lack presence).
- Explicit pause beacon: on pause and on the player's existing lifecycle
  pause paths (player.js has robust pagehide/freeze/visibilitychange
  handling ~line 1947/2922), send a small state update (`state:'paused'`,
  final position) via `navigator.sendBeacon`/keepalive fetch. Delivery is
  NOT guaranteed - the TTL degradation path (ruling 5) is the fallback,
  not an error.
- Poll: on shell load + every ~30s while visible; stop on hidden; re-poll
  on visibilitychange-to-visible. Guard against the v1.45 cached-view
  listener-leak class: ONE interval owned by the shell, not per-view.

### Server

- In-memory presence store, per user: `Map<userId, Map<deviceId, entry>>`
  where entry = `{deviceLabel, mediaId, kind, position, duration, state,
  lastSeenAt}`. HARD CAPS: bounded devices per user (evict oldest), label
  length-capped, deviceId length/charset-capped. Prune expired entries on
  read and write - no sweeper timer needed at this scale, but the
  implementer decides and documents.
- Writers: ALL THREE progress handlers accept the optional device fields
  and update presence - `/api/progress` (server.js ~9041),
  `/api/music/progress` (~7420), `/api/podcasts/progress` (locate it).
  Existing validation and 400/404 semantics BYTE-IDENTICAL for clients
  that omit the fields (backward compat: an old cached client must keep
  working, minus presence).
- Pause beacon endpoint (or a `state` field on the same handlers -
  implementer's call; prefer fewer new routes).
- `GET /api/handoff` (or `/api/presence` - name it once, keep it): takes
  the requesting deviceId (query param), returns the most recent
  OTHER-device presence for `req.user.id` or nulls. Includes what the
  card renders: label, mediaId, kind, title/thumb (resolve server-side
  from metadata - do NOT trust client-supplied title), position,
  duration, state, ageSeconds.

### Constants (initial values; tune only with reason, record the reason)

- ACTIVE_TTL: 15s (playing -> considered paused when pings stop)
- LINGER_TTL: 30min (paused -> expired)
- POLL_INTERVAL: 30s, visible-tab only
- DEVICE_CAP per user: 8, evict oldest lastSeenAt

## Named attack surfaces (the adversarial seat's brief - carry these
verbatim into the gate task prompt)

1. **Presence map growth**: unbounded (user x device) keys - incognito
   tabs mint fresh UUIDs forever. Demand the cap + eviction proven by
   test; try to leak memory past it.
2. **deviceLabel injection**: client-supplied string rendered in the
   card. XSS via label; over-length labels; empty/whitespace labels.
   Must be rendered as text (textContent), length-capped server-side.
3. **Cross-user isolation**: presence keyed strictly by `req.user.id`
   from the auth gate - hunt any path where a client-supplied id leaks
   into the key. User A must NEVER see user B's presence.
4. **`__proto__`/`constructor` as deviceId or mediaId** (the v1.42
   row-key lesson): the presence Maps are real Maps (safe) - verify no
   plain-object index sneaks in anywhere in the chain.
5. **Backward compat of the three progress handlers**: a ping WITHOUT
   device fields (old client, Roku) must behave byte-identically to
   today - status codes, stored progress shape, watched-latch behavior.
   Mutation-test: break the piggyback and confirm progress still flows.
6. **Ordering edges**: pause beacon arriving AFTER a newer play ping
   (same device, network reorder); stale beacon must not clobber a newer
   playing state - compare timestamps/lastSeenAt, prove with a test.
7. **Self-exclusion**: the card must never offer the device its own
   playback. Try deviceId omitted/blank on the GET.
8. **SPA nav staleness + listener leak**: card in the persistent shell,
   one poll interval total; navigate repeatedly and count listeners/
   timers (the v1.45 class). Verify the card survives in-app nav (the
   v1.38 `#view-root` class).
9. **The linger window vs history**: after LINGER_TTL expiry the card
   disappears but plain resume still works - verify the degradation is
   graceful, not an error.
10. **Restart amnesia**: server restart clears presence - the GET must
    return clean nulls, the client must handle them silently.
11. **Same-item two-device fight**: confirm the disclosed residual's
    actual behavior matches the disclosure (last-writer-wins, no
    corruption, watched-latch still sticky).

## Acceptance criteria (each becomes at least one test; suite-measured,
never projected)

- AC1: While media plays on device A, `GET` from device B (same user)
  returns that presence with state `playing`, correct kind, label, and a
  position no staler than one ping interval.
- AC2: Pause on A (beacon path) flips state to `paused` with final
  position; entry survives until LINGER_TTL, then expires (fake timers).
- AC3: Ping cessation WITHOUT a beacon degrades `playing` -> effectively
  paused/last-seen after ACTIVE_TTL; still lingers; still offered.
- AC4: The card renders on the top-level surfaces in ALL FOUR era skins,
  tokens only, both states (live dot / paused + age), thumbnail progress
  bar proportional to position/duration.
- AC5: Continue navigates to the kind-correct surface for all three
  kinds and playback resumes at the near-live position via the EXISTING
  resume paths (no new position plumbing).
- AC6: Dismiss suppresses that (mediaId, deviceId) presence across SPA
  navs; a NEW item or state change on the same device re-surfaces it.
- AC7: Self-presence is never shown (same deviceId).
- AC8: No DB schema change; restart clears presence; GET returns nulls
  cleanly for a presence-less user.
- AC9: Cross-user isolation proven by a two-user test.
- AC10: Old-client pings (no device fields) leave all three progress
  handlers byte-identical (existing suites stay green untouched - any
  edit to an existing progress test is a red flag to the gate).
