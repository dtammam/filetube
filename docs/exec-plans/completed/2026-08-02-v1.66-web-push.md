## Goal

When a download lands in the bell feed, subscribed devices get a Web Push
notification - including the iOS home-screen PWA. No new server deps: VAPID
(RFC 8292) and payload encryption (RFC 8291, aes128gcm) in raw `node:crypto`.

## Rulings this plan implements (approved; verbatim source in the handoff)

1. Scope: new-download pushes only; the bell feed's AUTOINCREMENT ids are the
   delivery cursor (designed for this since v1.51 - the in-code comment at
   `lib/db/sqlite.js:377` reserves exactly this seam).
2. iOS: works only for the home-screen-installed PWA; permission prompt must
   come from a user gesture -> "Enable notifications" button in Settings;
   per-device subscribe; per-user opt-out.
3. The service worker is PUSH-ONLY - no fetch/cache handlers, ever.
4. P1: new `push_subscriptions` table keyed UNIQUE by endpoint; user_id
   cascade; p256dh/auth; per-subscription `last_pushed_id` cursor. Carrier
   discipline in the same commit.
5. P2 catch-up: <=3 missed rows -> individual pushes; more -> ONE summary
   push ("N new videos"); cursor advances to newest either way.
6. P3 failures: 410/404 -> prune the subscription; 429 -> honor Retry-After
   (cooldown) else skip the round; 5xx -> skip the round; the cursor makes
   the next feed event retry naturally. Delivery is fire-and-forget - it can
   never block or fail a download or scan.
7. P4: double-notify suppression lives in the SERVICE WORKER
   (`clients.matchAll` visible-window check), not the server.

## Design

### D1. Schema v7 (Commit A)

```sql
CREATE TABLE IF NOT EXISTS push_subscriptions (
  endpoint TEXT NOT NULL PRIMARY KEY,
  user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  p256dh TEXT NOT NULL,           -- base64url uncompressed P-256 point (65 bytes decoded)
  auth TEXT NOT NULL,             -- base64url 16-byte auth secret
  last_pushed_id INTEGER NOT NULL DEFAULT 0,
  cooldown_until INTEGER NOT NULL DEFAULT 0,  -- epoch ms; 429 Retry-After honor
  created_at INTEGER NOT NULL     -- epoch ms
);
```

Epoch-ms INTEGER times per the v5 convention (numeric comparisons).
`SCHEMA_VERSION` -> 7; forward-only `if (current < 7)` block; header-comment
paragraph added.

### D2. Backup/restore: DELIBERATE exclusion (the one carrier deviation)

Push subscriptions do NOT ride backup bundles. Three reasons, in the repo's
own posture:

1. Secrets don't ride bundles (`server.js:7482` states it for the session
   secret): `auth` is a shared secret; the endpoint URL is
   capability-bearing.
2. Subscriptions are cryptographically bound to THIS instance's VAPID key
   (browsers pin the applicationServerKey at subscribe time). Restoring them
   onto another instance - whose VAPID key deliberately does not ride the
   bundle either - yields rows that can never deliver.
3. The failure self-heals: the client boot reconcile (D7) re-POSTs the
   browser's live subscription whenever the server lacks it.

Mechanics: no `exportUsersForBackup` field, no validator entry, no restore
branch. A restore WITHOUT a `users` key leaves subscriptions untouched (rows
hang off untouched user rows). A restore WITH `users` wipes them via cascade;
devices re-register on next visit via the reconcile. Disclosed in ROADMAP.
The plan calls this out so reviewers score it as a decision, not a miss.
Carrier seams that DO apply, same commit: `__clearUserStateForTests` DELETE,
cascade FK + binding test. Media-id seams (`removeMediaState`/
`rekeyMediaState`) do NOT apply - subscriptions are not media-keyed.

### D3. VAPID keys (Commit B)

`lib/push/keys.js`, structural copy of `resolveSessionSecret`:
`DATA_DIR/vapid-keys.json` `{ publicKey, privateKey }` (JWK), created
`{ mode: 0o600 }` + best-effort chmod, minted via
`crypto.generateKeyPairSync('ec', { namedCurve: 'prime256v1' })` on first
boot, validated fail-closed on load (curve, key sizes, pub-matches-priv).
Resolved once at boot next to `server.js:189`. Never in bundles (DATA_DIR
file, not db - free). `FILETUBE_VAPID_SUBJECT` env sets the JWT `sub`
contact (default `mailto:admin@filetube.local`).

### D4. Crypto (Commit B) - `lib/push/vapid.js`, `lib/push/encrypt.js`

- VAPID JWT: ES256; header `{typ:'JWT',alg:'ES256'}`; claims
  `aud` = ORIGIN OF THE PUSH ENDPOINT (never FileTube's - no base-URL config
  needed), `exp` = now + 12h (RFC 8292 max 24h), `sub` = contact. Signature
  via `crypto.sign('sha256', data, { key, dsaEncoding: 'ieee-p1363' })` -
  raw r||s, NOT DER (the classic implementation trap; unit test verifies
  round-trip with `crypto.verify` AND asserts 64-byte signatures).
  Header: `Authorization: vapid t=<jwt>, k=<base64url uncompressed pubkey>`.
- RFC 8291 encryption: ephemeral P-256 ECDH against `p256dh`;
  HKDF chain per the RFC (`WebPush: info\0` || ua_public || as_public;
  CEK via `Content-Encoding: aes128gcm\0`, nonce via
  `Content-Encoding: nonce\0`); body = salt(16) || rs(4, 4096) ||
  idlen(1)=65 || ephemeral pubkey(65) || AES-128-GCM ciphertext of
  plaintext || 0x02 delimiter. Single record.
- BINDING: the encrypt function takes injectable salt + ephemeral keypair so
  the unit test replays RFC 8291 Appendix A end-to-end and asserts the EXACT
  final body bytes (vectors transcribed from the RFC text at implementation
  time, never from model memory).
- Payload: JSON `{ title, body, url }` - the icon is NOT in the payload, the
  worker hardcodes `/icons/icon-192.png` (D7). Title and body clamp at 120
  chars each; the encoder refuses plaintext over `MAX_PLAINTEXT` (4079 =
  the 4096 record minus the delimiter and GCM tag).

### D5. Delivery (Commit C) - `lib/push/deliver.js`

Deps-injected (`request` impl, `guardHop`, store, clock, log) so the whole
policy is unit-testable without a network. Flow per delivery round:

1. Feature gate: `notificationsFeatureEnabled(db)` false -> no-op.
2. For each subscription (skip `cooldown_until > now`; skip users whose
   mirrored `pushEnabled === 'off'`): rows = feed WHERE id > last_pushed_id
   ORDER BY id.
3. Collapse per P2: <=3 -> one push per row (title = video title, body =
   channel, url = /watch.html?id=...); >3 -> ONE summary ("N new videos",
   url = /). Titles resolved via injected metadata resolver.
4. Per POST: `guardHop(endpoint)` refuse -> treated as dead (prune);
   redirects NOT followed (3xx = failure, skip); hard timeout; headers
   `TTL: 86400`, `Urgency: normal`, `Content-Encoding: aes128gcm`,
   VAPID auth.
5. Status handling per P3: 2xx -> advance `last_pushed_id` (summary:
   all-or-nothing; individual: advance per delivered row, in id order,
   stop at first failure); 404/410 -> DELETE the row; 429 -> set
   `cooldown_until` from Retry-After (default 10 min, cap 24h); anything
   else -> skip round.
6. Trigger: `server.js:4856` flush site fires `void deliver(...).catch(log)`
   DETACHED (never `await` - `runScanDirectories` gates the scan-coalescing
   state machine; the `preExtractCandidates` loop below it is the precedent).
   Seeding and restore paths never call it.

### D6. Routes (Commit D)

- `GET /api/push/key` -> `{ key }` (base64url uncompressed public point).
  Auth-gated.
- `POST /api/push/subscribe` `{ endpoint, keys: { p256dh, auth } }`:
  https-only endpoint, length caps, base64url shape checks on keys,
  `guardHop` refuse -> 400; per-user cap 10 subscriptions -> 409 beyond;
  upsert keyed by endpoint (re-subscribe re-binds to the current user);
  cursor initialized to current `MAX(notifications.id)` - a fresh device
  never gets back-flooded.
- `POST /api/push/unsubscribe` `{ endpoint }`: deletes the row only if owned
  by the caller.
- Per-user opt-out: `pushEnabled` joins `MIRRORED_SETTING_KEYS`
  (`'on'`/`'off'` strings - zero validator surgery; absent = on). Note:
  adding a mirrored key touches no locked global-settings suite (those lock
  `DEFAULT_SETTINGS`/`/api/settings`, a different lane) - verified at
  implementation time.
- All three routes 404 behind `notificationsFeatureEnabled` (the bell's
  gate), join the route census, and are NOT in `READONLY_ALLOWED_POSTS`.

### D7. Client + SW (Commit E)

- Auth allowlist: `/push-sw.js` joins `ALLOW_EXACT` (static trusted code, zero

- `common.js`: shedder exempts `/push-sw.js`; boot reconcile (authenticated

- `setup.html`/`setup.js`: "Push notifications" block directly below the

## Gate brief (both seats get this plan + these named attack surfaces)

Full gate (real crypto + a new remote-write primitive). Adversarial seat
FIRST (it mutates; byte-identical restore proven), then QA. Attack surfaces:

1. THE CRYPTO IS A FRONT-DOOR LOCK. Verify the RFC 8291 vector test is
   BINDING (mutate the encrypt function - the exact-bytes assertion must
   kill every mutant); check p1363-vs-DER, aud derivation (endpoint origin,
   never ours), exp bounds, key file perms, JWK validation fail-closed.
2. SUBSCRIPTION-ENDPOINT SSRF: the endpoint is attacker-controlled remote-
   write. Attack subscribe AND delivery-time guards, redirect handling
   (must refuse, never follow), DNS tricks vs `guardHop`'s envelope,
   read-only mode, the per-user cap, cross-user unsubscribe.
3. THE LOCK AMENDMENT: prove the re-scoped v1264 suite still refuses a
   fetch handler, a caches reference, a second register site, and a shedder
   that stops shedding foreign SWs.
4. DELIVERY CAN NEVER HURT THE SCAN: prove a hanging/throwing transport
   never blocks `runScanDirectories`, never double-fires, never pushes from
   seeding or restore; the v1.30 AC4.2 write-amplification lock stays green
   (cursor updates are per-delivery, not per-scan-no-op).
5. CARRIER DEVIATION D2: attack the deliberate bundle exclusion - prove a
   users-restore + reconcile round-trip actually re-registers, and that no
   secret (VAPID private, auth, endpoint) appears in any bundle.
6. Payload privacy: titles ride encrypted; nothing sensitive in the
   mutation-audit log line (endpoint not in URL path).
