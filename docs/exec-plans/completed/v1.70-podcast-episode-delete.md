## Machine-derived facts (measured 2026-08-02 at v1.69.1 / main 01edeb4)

- **F1 - the cover bug, REPRODUCED LIVE against Dean's real feed.** The
  channel <itunes:image> is a 3000x3000 PNG of **15,494,765 bytes**;
  COVER_MAX_BYTES = 8 MB (lib/podcasts/index.js). With the production cap
  the shipped pipeline returns `{ok:false, error:"enclosure exceeds the
  size cap"}` (no leftovers - the .ptpart discipline held); with no cap
  the SAME pipeline downloads it fine (guard chain, UA, redirect, naming
  all correct). COMPOUNDING BUG: the attempt is gated on
  `targets.length > 0`, so once the backfill completes the cover is never
  retried - one oversized-art failure is permanent. And it is silent by
  design (best-effort), so nothing told anyone.
- **F2 - the trash seam is pure and podcast-ready.** lib/trashPaths.js:
  `computeTrashTarget(filePath, id, matchedRoot, nowMs)` ->
  `<matchedRoot>/.filetube-trash/<nowMs>-<id8>-<basename>`. matchedRoot =
  the podcasts root -> same filesystem -> atomic rename. All three scan
  walkers already skip TRASH_DIR_NAME; the podcasts module has no walker
  that would index it (sweepPartFiles only unlinks dot-prefixed .ptpart
  names; reconcile checks stored filePaths).
- **F3 - retention setting exists.** db.settings.trashRetentionDays,
  validated to {0,7,14,30,90} (server.js TRASH_RETENTION_DAYS_VALID_VALUES,
  0 = keep forever). The v1.65 sweep serves db.trash only; podcasts adds
  its own sweep over its own records (deliberately separate - db.trash
  records are metadata-shaped and restore into db.metadata; tech-debt #81's
  reasoning stands, this wave builds the podcasts-owned lane it named).
- **F4 - episode records already carry the archive law**: status
  'tombstone' blocks re-download forever; reduceEpisodeStatus clears
  filePath on tombstone/deleted-on-disk. Per-user rows purge via
  removePodcastEpisodeState (the TENTH carrier's delete half).

## Design

- **D1 - cover fix (3 parts, all bound by tests).** (a) COVER_MAX_BYTES
  8 MB -> 32 MB (2x headroom over the measured 15.5 MB real-world shape).
  (b) Decouple the attempt from `targets.length > 0`: try whenever the
  feed offers imageUrl, no cover file exists, and the show dir exists (or
  this cycle creates it) - a failed attempt retries on EVERY poll until
  art lands. (c) Surface failure: append `cover art failed (<transport
  error>)` to the cycle's status parts (redacted lane, like every other
  part) - never again silent.
- **D2 - episode trash lane (store).** New episode status **'trashed'** +
  fields trashPath/trashedAt. Reducers: reduceEpisodeTrashed (from
  'downloaded' only), reduceEpisodeRestored (from 'trashed' only; restores
  filePath, clears trashPath), selectExpiredTrashedEpisodes(episodes,
  retentionDays, nowMs) (pure; retentionDays 0 -> never expires). VALID
  statuses set grows by 'trashed'; publicEpisode exposes status +
  trashedAt (never trashPath - server paths don't leak).
- **D3 - routes.** DELETE /api/podcasts/episodes/:id: only status
  'downloaded'; computeTrashTarget(filePath, id, podcastsRoot, now) ->
  mkdir trash dir -> rename (EXDEV -> copy+fsync+verify-size+unlink, the
  v1.65 posture) -> ONE mutation flips the record. Per-user rows are KEPT
  (episode ids are guid-derived and unchanged; restore must find
  progress/played intact). POST /api/podcasts/episodes/:id/restore: only
  'trashed'; destination = original filePath; REFUSE if a file already
  occupies it (409, never clobber); rename back -> record flips to
  'downloaded'. Both 400 on wrong states; phantom ids get 404 (AMENDED
  at the QA gate: the plan said 400 for both, the implementation
  returns 404 for a phantom id - the more correct side, matching every
  other podcasts route's no-such-episode posture; tests bind 404).
  /episode/:id
  already 404s for non-'downloaded' (filePath cleared? NO - trashed keeps
  filePath for restore; the route's status!=='downloaded' check covers it
  - and gate history says that check is currently redundant-but-unbound
  (MP9); it now becomes LOAD-BEARING and gets a binding test).
- **D4 - retention.** Each poll cycle end + boot: selectExpired... over
  db.settings.trashRetentionDays -> unlink trash file (best-effort; a
  missing trash file still tombstones) -> status 'tombstone' + clear
  trashPath -> removePodcastEpisodeState (purge rows at PURGE, matching
  v1.65: trash keeps state, purge retires it). Never runs when the
  podcasts root is absent (mount-loss guard 1) and never touches
  non-'trashed' records.
- **D5 - UI.** Downloaded rows get a delete control (two-tap confirming,
  the unsubscribe pattern: "Delete? Recoverable from trash for N days" /
  "forever" when retention 0... honest either way); trashed rows show a
  'In trash' chip + Restore button; restored rows resume exactly where
  they were (rows kept). Backup: trashed episodes ride db.podcasts as-is
  (records already in the bundle; trashPath is a server path inside the
  podcasts root - same class as filePath, which already rides).
- **D6 - deliberately OUT:** bulk delete (ruling 2), auto-delete-after-
  played, in-flight download abort (#84), db.trash integration (#81's
  reasoning - closes #81 via this podcasts-owned lane instead).
