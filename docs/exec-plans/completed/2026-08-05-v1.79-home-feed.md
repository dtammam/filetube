# v1.79.0 - Home feed: a library with a YouTube feel

Status: SHIPPED v1.79.0 (docs reset 2026-08-15; see ROADMAP.md). Was: ACTIVE - intake complete (Dean, 2026-08-05). Version target: v1.79.0.
Implementing session: Opus. Full two-reviewer gate (per-user data aggregation).

## The ask, verbatim intent

Dean wants the home page to gain a YouTube-style **feed** - horizontal rows of
"Continue watching," "New from your subscriptions," "Recently added," per-channel
"More from X," etc. - as an **opt-in mode** that a user toggles on, leaving the
current flat sorted grid ("the legacy classic file-system experience") available
and unchanged for those who prefer it.

## The thesis (Dean, at intake)

> "What's new in the library, not what's new to watch. That's the point. This is
> not simply a YouTube thing. It's a library thing with a YouTube feel."

The feed re-surfaces your OWN library (the half-watched video, the new uploads
from a channel you follow, the thing you liked last month). It is a
**re-engagement home, not a recommender** - every row is labeled, deterministic,
and explainable. No collaborative filtering, no opaque "Recommended for you."

## Framing: what already exists vs. what is genuinely new

The home is more built-out than a fresh feed would assume. It ALREADY renders
three horizontal rows above the grid, client-assembled, capped at
`HOME_ROW_CAP=8`, each gated by a device-local visibility toggle
(`homeRowEnabled`, localStorage `ft-home-*`):

- **Continue watching** (video) - `buildVideoHomeSectionHtml` (main.js:223),
  data from `GET /api/videos?filter=recent-watching` (server.js:8845).
- **Continue listening** (music + podcast, merged by recency) -
  `buildListeningHomeSectionHtml` (main.js:165).
- **Continue reading** (books) - `buildBooksHomeSectionHtml` (main.js:129).

The horizontal-row CSS chassis (`.books-home-row` / `-scroller` / `-seeall`,
style.css:7450) and per-kind card builders (`buildVideoRowCardHtml`,
`buildMusicRowCardHtml`, `buildPodcastRowCardHtml`, `buildBookRowCardHtml`)
already exist and are reused verbatim - this wave writes almost no new card CSS.

**What is genuinely new, and the ENTIRE scope of this wave:**

1. **The feed-vs-classic toggle** - a per-user Settings switch (`homeFeed`
   `'on'`/`'off'`). Today it is "grid always, optional rows on top," not a mode.
2. **The missing rows** - New-from-subscriptions, Recently-added (explicit),
   per-channel "More from X", Popular-in-your-library, Watch-again.
3. **Server-side per-user assembly** - a new `GET /api/home` endpoint that
   assembles the whole row structure per-user (mirroring v1.78's server-resolved
   `GET /api/handoff`), so it is RBAC-ready for the next tranche and testable in
   one place.

## Locked intake decisions (Dean, 2026-08-05)

1. **Rows, source-agnostic.** A "More from X" row works whether X is a subscribed
   YouTube channel or a local folder. Row roster (top to bottom):
   Continue watching -> New from subscriptions -> Recently added ->
   per-channel (top ~2-3 most-watched) -> Popular / Watch-again (tail).
2. **Toggle, not replace.** Feed mode is a distinct render path; **classic mode
   is today's home, byte-untouched** (zero regression risk to the existing
   rows/grid). A per-user Settings switch chooses.
3. **Deterministic + explainable** ordering for v1. No collaborative filtering.
4. **New per-user `GET /api/home`** endpoint assembles the rows server-side.
5. **Horizontal scroll rows**, YouTube-home style, all four era skins + mobile,
   tokens only. In feed mode the classic controls (format/watch/sort) are
   **abstracted out** (not shown) - the rows encode the intent; classic keeps
   them.
6. **Mixed media** - the three player-carried kinds: video, music tracks,
   podcast episodes (yt-dlp MP3s included). Books stay on their own surfaces
   (different resume model). Endpoint widened accordingly.

**Default:** the `homeFeed` setting is **absent (=> classic)** for existing
installs - nobody's home changes silently - and **seeded `'on'` at user
creation** so every net-new setup/account gets the YouTube feel out of the box.

**Disclosed limitation (honest, not a bug):** subscriptions are GLOBAL/SHARED
until the v1.44 RBAC tranche builds per-user subscription lists
(`store.listSubscriptions` reads the shared DB, not keyed by user). So the
"New from **your** subscriptions" row is really "new from **the** subscriptions"
today; it becomes genuinely per-user for free when RBAC lands. Continue-watching,
per-channel, Popular and Watch-again are already truly per-user (progress is
per-user as of v1.43).

## Architecture

**One view, two render paths.** The existing `home` SPA view (main.js:453,
registered main.js:2048) branches at init on the resolved `homeFeed` setting:

- **classic** (default): today's path exactly - controls mounted, grid fetched,
  existing continue-rows injected. Not touched by this wave.
- **feed**: fetch `GET /api/home`, render the returned rows into a feed host via
  the existing section/card builders + the new row types. Classic controls are
  NOT mounted. No infinite grid; "Recently added" carries a `See all ->` into
  the classic browse as the escape hatch.

**`lib/home/feed.js`** - a PURE leaf module (mirrors `lib/presence/store.js`):
given already-fetched inputs (library items with per-user progress/watched
overlay, the music/podcast in-progress lists, the subscription->folder map,
per-media watch counts), it returns the ordered, capped, de-duplicated row
structure as **id + metadata only**. It never touches the DB, the request, or
rendering. The `GET /api/home` route gathers inputs, calls the assembler, and
resolves each id to render-ready fields (`{id, kind, title, subtitle,
thumbnailUrl, href, progressPercent}`) SERVER-side - the client supplies
nothing, exactly like `resolveHandoffTarget` (server.js:9161). Named + exported
row-selector functions so each is bindable by test (the v1.73 W1 lesson).

**Per-user setting.** Add `homeFeed` to `MIRRORED_SETTING_KEYS` (server.js:5454);
value `'on'`/`'off'` (bounded-string, like `pushEnabled`/`starRatings`); written
client-side via `mirrorUserSetting({homeFeed})` (common.js:119); seeded on boot
from `/api/auth/me`. Seed `'on'` in the user-creation path so net-new users
default to feed; absent resolves to classic (existing installs unchanged).

## Row definitions (the pure selection rules the gate binds)

Uniform cap `HOME_ROW_CAP = 8` (existing). Empty rows are omitted entirely.
"Finished" = latched watched OR `progressPercent >= WATCHED_PCT (90)`
(`lib/videoQuery.js`); "in progress" = a saved position (`timestamp > 0`) and
not finished - the SAME predicate `/api/videos?filter=recent-watching` uses
(no `> 0.5` floor; consistency with the already-shipped Continue-watching row
outranks a new threshold).

1. **Continue watching** - in-progress items across all three kinds, ordered by
   progress `updatedAt` DESC, capped. (Reuses the recent-watching /
   recent-listening selections, merged.) No See-all (mixed destinations).
2. **New from subscriptions** - items whose folder maps to a subscription,
   ordered newest-first (release-date/scan), **unwatched first**, capped. Hidden
   when there are no subscriptions or no unseen items. Carries a "New" count cue
   derived from the existing watched-state machinery. See-all -> the subs browse.
3. **Recently added** - newest items library-wide, ALL kinds, **watched items
   included** (this is "what's new in the library"), capped. Always present -
   the fallback so the feed is never blank. See-all -> classic browse
   (newest sort).
4. **More from <channel/folder>** - for the user's top ~2-3 most-watched
   channels/folders (by per-user watch count), one row each of that source's
   items (recency), capped. See-all -> that folder.
5. **From your Liked** - explicitly-liked items across all kinds, most-recently-
   liked first, capped. See-all -> /playlists. Hidden when empty (no floor - one
   favorite is a real row). **Replaces the "Popular in your library" row from
   intake:** the store has NO per-item view count (`user_watched` is a boolean
   latch, `completed_at`, `ON CONFLICT DO NOTHING`), so a true popularity number
   does not exist to surface - building a row on a number we do not have would
   violate the honesty norm. The per-channel rows (4) already carry the truest
   "most-watched" signal the store DOES have: the COUNT of completed items per
   folder. Disclosed to Dean in the release report.
6. **Watch again** - finished (latched) items, most-recently-finished first,
   capped. Hidden when empty.

Row ORDER is fixed (deterministic); within-session STABILITY: the feed is
fetched once per home entry, not reshuffled on scroll.

## Acceptance criteria (numbered, testable)

- **AC1** `GET /api/home` requires auth; returns `{ rows: [...] }`; each row
  `{ id, kind, title, seeAllHref|null, items: [...] }`; each item carries only
  server-resolved fields (id, kind, title, subtitle, thumbnailUrl, href,
  progressPercent). No client-supplied field is ever echoed.
- **AC2** Every row is capped at `HOME_ROW_CAP`; empty rows are omitted; the
  Recently-added row is always present for a non-empty library.
- **AC3** Continue-watching excludes finished items and spans video+track+
  podcast, ordered by progress recency. (Bind: a finished item never appears; a
  paused-midway item of each kind does.)
- **AC4** New-from-subscriptions only includes items under a subscription folder;
  unwatched sort ahead of watched; the row is absent with zero subscriptions.
- **AC5** Recently-added INCLUDES watched items (the thesis) and is newest-first.
- **AC6** Per-user isolation: two users with different progress/watched/liked get
  different Continue-watching, From-Liked, Watch-again, and per-channel rows from
  the SAME library (mirror the v1.78 cross-user isolation AC).
- **AC7** Prototype safety: media/track/podcast ids of `__proto__`/`constructor`
  resolve to nothing, never a phantom row item (own-property checks throughout,
  the v1.42 row-key lesson).
- **AC8** `homeFeed` setting: absent => classic; `'on'` => feed; round-trips
  through `POST /api/me/settings` (allowlisted, regex-bounded); a net-new user is
  created with `homeFeed:'on'`; an existing user (no key) stays classic.
- **AC9** Classic mode is byte-unchanged: the classic render path, its controls,
  and the existing continue-rows are not modified (diff shows only additive
  branches). A `homeFeed:'off'` / absent user sees exactly today's home.
- **AC10** Feed mode mounts no format/watch/sort controls; renders rows via the
  existing builders; "Recently added" See-all navigates to the classic browse.
- **AC11** Tokens-only: `npm run lint:css` count unchanged (no new raw literals);
  `npm run ledger:check` green. Any new CSS reuses `.books-home-row`.
- **AC12** All four era skins + mobile render the feed (rows inherit era styling
  via tokens; no per-era rule needed).

## Named attack surfaces (for the adversarial seat)

- **S1 Cross-user bleed** - `/api/home` assembles from per-user progress/watched;
  prove user B never sees A's Continue-watching/Popular/Watch-again ordering.
- **S2 Prototype pollution** - ids `__proto__`/`constructor` through every
  per-kind resolver arm (media/track/podcast) and the subscription-folder map.
- **S3 Client-supplied trust** - confirm no client field (title/href/thumbnail)
  is ever echoed; every display field is server-resolved.
- **S4 Dead-link offers** - a deleted/trashed/pruned/non-downloaded item must not
  appear as a row card (the handoff `resolveHandoffTarget` null-skip rule).
- **S5 Classic regression** - prove the classic render path + existing
  continue-rows are byte-unchanged; a `homeFeed`-absent user is unaffected.
- **S6 Setting injection** - `homeFeed` must survive only through the allowlist +
  regex; a junk value must not persist or crash the resolver.
- **S7 Empty/degenerate** - brand-new user (no progress, no subs, empty library):
  the feed must degrade gracefully to Recently-added or an honest empty state,
  never throw.
- **S8 jsdom leak** - any new client test that boots common.js must
  `window.close()` (the v1.78.1 suite-hang scar).
