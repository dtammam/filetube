## Item 1 - full descriptions (DONE)

**The brief's assumption was wrong and this is worth remembering: the
truncation was RENDER-ONLY. No reheat or backfill work was needed or done.**

Verified end to end that the full text was always present:

- `--embed-metadata` is passed unconditionally (`lib/ytdlp/args.js:1148`).
- ffprobe reads format tags under `maxBuffer: 16MB` (`server.js`), a ceiling
  whose own comment says it was raised specifically for long descriptions.
- `parseFfprobeTags` whitelists `description` and only trims whitespace.

Two client defects produced the symptom:

1. The description was never rendered in the description box at all.
   `#description-paragraph` is static boilerplate ("File Path: ... This file is
   self-hosted on your network..."). The description appeared only as one row of
   the "Embedded info" block, cut to 400 chars by `renderEmbeddedTags`'s `clip`.
2. `-webkit-line-clamp` lived on that boilerplate, so "Show more" expanded three
   lines of static text and never any description.

Fix: the description is its own element (`#video-description`) carrying
`.description-text`, so the existing clamp/expand mechanism now governs it. The
boilerplate moved to an unclamped `.description-fileinfo`. `description` is
skipped by `renderEmbeddedTags` (it would otherwise print twice, once clipped).
The 400-char clip survives for every OTHER tag, where it still guards layout.

`resolveDisplayDescription` (pure, exported, 10 unit tests) owns the display
decision. Its title-equality guard is load-bearing: for universal-lane items the
title IS the description (`%(title).100s`, v1.41.16-18), so without it those
items print the same text twice. The guard is equality, deliberately NOT prefix.

## Item 2 - real view counts (DONE)

**The single most important fact: the field is `sourceViewCount`, never
`viewCount`.** `item.viewCount` was already taken - the legacy pre-v1.42 LOCAL
watch counter, still honored as a floor by `effectiveViewCount`. Using that name
would have made a fresh download report ~12M local plays on the stats page.

Second trap: yt-dlp emits `view_count` as a JSON NUMBER, and run.js's `present()`
helper only passes non-empty STRINGS. Routing it through `present()` would have
nulled every count - dead on arrival with a green suite (the v1.47.4 class).
`presentNumeric` handles it and preserves a genuine `0`.

Flow: both `--print` selectors -> `presentNumeric` -> `store.parseCapturedViewCount`
(non-negative integer; rejects floats/NaN/Infinity/negatives; 1e15 ceiling) ->
persisted WITH its capture date as a unit.

Carriers updated in the same commit (v1.42 lesson): changed-file re-init
carry-forward, and BOTH halves of the Phase-2 merge (completed-mid-scan adoption
+ partial-reheat gap-fill). Also joined run.js's "anything usable" gate and
index.js's `hasAnythingToPersist` chain. Move re-key and backup/restore already
carry it (whole-item move, wholesale namespace).

Reheat SUPERSEDES (re-snapshotting is the feature) and is network-only, so a
reheat that cannot reach the network never destroys a stored count.

Render: watch page "1.2M views when downloaded"; cards bare. No capture -> mock
count retained (a library of "0 views" would look broken; fake stars stay).

## Item 4 - modernise old mock commenters (DONE)

**It is not a code bug.** A line-joined whole-tree scan found ZERO real names
left in source (only `ROADMAP.md` describing the v1.44.3 incident, and
`package.json`'s legitimate `"author": "Dean Tammam"`). The current
`MOCK_COMMENT_BANK` is fully genericised.

The names live in **Dean's browser localStorage**. `watch.js`'s `loadComments`
writes generated comments to `comments_${mediaId}` on a video's FIRST view and
never regenerates:

```js
const localComments = localStorage.getItem(savedCommentsKey);
if (localComments) { comments = JSON.parse(localComments); }
else { comments = getMockInitialComments(); localStorage.setItem(...); }
```

So every video opened before v1.44.3 has the pre-genericisation names frozen
client-side. Dean confirmed three of them from memory; the actual retired set is
NINE (v1.44.3 + v1.44.4). The names are deliberately NOT reproduced in this
document or in the tests - see the fix round below.

**THIS CAN LOSE DATA**, so the shipped fix is a reconciliation, not a reset.
Dean's own posted comments live in the same array under `author: 'You'`;
versioning the storage key would have silently deleted every real comment he has
written. `reconcileStoredComments` keeps every `'You'` comment in its original
order and at the front, drops only entries whose author is absent from the
current bank, and regenerates the mock remainder. The already-current path
returns the stored array instance untouched, so there is no localStorage write on
a normal page load.

Dean was also given the targeted manual reset for his own browser (clear only
`comments_*` keys), since the migration cannot reach devices he does not open.

## Item 6 - duplicate file after a one-off (WITHDRAWN)

Dean withdrew this: he could not reproduce a duplicate and said not to conflate
it with anything else. **No duplicate-detection and no reaper work was done, and
that remains the right outcome** - this repo shipped a file-destroyer of exactly
that class once already (v1.41.6).

Kept for the record, since it cost real investigation: the two paths he reported
differed only by the ` [<id>]` bracket, from a YouTube URL. Ruled out during
diagnosis - `lib/ytdlpIntermediates.js` cannot match a bracket-less file (every
pattern is anchored to the 11-char id bracket, deliberately, after the v1.15.1
hotfix-2 data-loss incident); background audio extraction writes to
`audioPath(id)`, a cache dir keyed by id; and yt-dlp's own templates always
produce a bracket, so the bracket-less copy was not written by our download argv.
The leading hypothesis had been a pre-existing bracket-less IMPORT (the shape
`relocateHydratedImportIntoChannelFolder` exists for), against which a fresh
one-off could not dedup because an import carries no `.ytdlp-archive.txt` entry.

### Where I deviated from a prescription (adversarial W4)

W4 was correct that the stale-name fixture was built from Dean's recollection and
covered 3 of 9 retired names. The prescribed fix - seed the fixture from the full
v1.44.3/v1.44.4 set - was NOT taken, because it would re-commit all nine real
names into the repository, which is precisely what those releases removed, and it
would still be a hardcoded list proving nothing general. Instead the tests prove
the property that actually matters: the purge is **name-agnostic**, decided solely
by absence from the current bank. A 200-author generated sweep pins it. All real
names were also removed from the test file and from this document. The
adversarial seat accepted this without reservation on re-confirm, and noted that
its own first report had printed all nine names into the gate record while
arguing for de-identification.

**Residual neither approach covers (adversarial S-D4):** if one of the retired
names were ever re-ADDED to the current bank, it would read as "current" and
never be purged. A hardcoded name list would have failed loudly there; the
name-agnostic sweep cannot see it. No clean detection exists - the usual
"two capitalised words" heuristic is useless because the bank legitimately holds
`My Wife`, `Proud Dad`, `Loving Daughter`, `Maligned Mentor` and similar. Noted,
not blocking.
