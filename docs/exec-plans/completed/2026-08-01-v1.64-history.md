## Design facts (machine-verified against main 88a18ff)

- `user_progress` (user_id, media_id, timestamp, duration, updated_at
  ISO; PK user+media) - lib/db/sqlite.js:286. `user_watched` (user_id,
  media_id, completed_at ISO; PK user+media) - lib/db/sqlite.js:359.
- `completed_at` is currently WRITE-ONLY (written by addWatched, read
  only by the backup export; the live getWatched discards it) - a
  newest-first merged history needs a new timestamped read statement.
- `delProgress` (store.js:58) is a DEAD prepared statement today - no
  method calls it. There is NO per-user watched delete and NO
  clear-by-user statement for either table. All net-new.
- The progress coalescer (server.js:709 `pendingProgress`, 5s debounce,
  key `${userId}:${mediaId}`) stages writes in memory. THE WAVE'S
  SHARPEST HAZARD: a history remove/clear that only deletes SQLite rows
  is resurrected <=5s later by the flush. Every destructive history op
  MUST also purge the matching staged entries.
- History adds NO new id-keyed carrier: it is a read + user-scoped
  destructive ops over two tables that have carried every seam
  (delete/rekey/backup/restore/test-reset) since v1.43/v1.50.
  db.viewCounts (global play counts) is NOT touched by history removal.
- The watched latch's "playback NEVER deletes a row" invariant comment
  (store.js:~481) gains its one legitimate exception: USER-INITIATED
  history removal. The comment must be updated in the same commit
  (stale-comment findings are a QA seat class).
- Removing history changes `?watch=watching|watched` filter results for
  that item (back to "new") - inherent to the feature, DISCLOSED.

## API

- `GET /api/history?offset&limit` -> `{items, total, offset, limit}`,
  newest first. Order key per media: max(progress.updated_at,
  watched.completed_at), with the user's staged pendingProgress entries
  overlaid as "now" (read-your-writes; an item paused 3s ago must lead
  the list). Items shaped like /api/liked (title, thumbnail, duration,
  progressPercent, watchState, lastWatchedAt...). Dead media ids
  filtered at read time (the shapedQueue pattern) - a progress row for
  a deleted file must not corrupt the page.
- `DELETE /api/history/:id` - per-item: delete the user's progress row
  + watched row + purge the staged coalescer entry. 404 never required
  (idempotent 200 {success}).
- `DELETE /api/history` - clear-all for THIS user only: user-scoped
  DELETEs on both tables + sweep staged entries where entry.userId
  matches. Cross-user isolation is an adversarial target.
- Scope: media library only (videos + audio in db.metadata). Music
  library (db.music) and books have disjoint progress namespaces and
  are OUT (the queue-wave precedent). Re-watching after a remove
  re-adds the item naturally (the ping re-stages, the latch re-marks) -
  correct and tested, not a bug.
