## Item 1 - Subtitle 429 aborts the whole download (ROOT-CAUSED)

### Verified against yt-dlp source, not docs

Verified against `yt_dlp-2026.7.4` (fetched via `pip download`, extracted and read
directly). The full causal chain, with line citations:

1. `lib/ytdlp/args.js:1125` passes `--write-auto-subs`, which sets
   `writeautomaticsub=True`.
2. `extractor/youtube/_video.py:4224` gates translated-subtitle construction on
   exactly that param: `get_translated_subs = 'translated_subs' not in
   self._configuration_arg('skip') and (self.get_param('writeautomaticsub', False)
   or ...)`. So OUR flag is what switches it on.
3. `extractor/youtube/_video.py:4287`: for a video whose MANUAL subtitles are
   translatable, every translation target produces a synthetic subtitle key
   `trans_code += f'-{lang_code}'` - including the exact key in Dean's error,
   `en-en-US` (a machine translation of the `en-US` manual track INTO English,
   which is redundant when we already fetch `en-US` itself).
4. `YoutubeDL.py:3182`: `--sub-langs` is matched with `use_regex=True`. Our
   `en.*` is therefore a REGEX, not a glob, and matches every key starting with
   `en`, which is what drags the redundant translated track in.
5. `YoutubeDL.py:4491` issues one HTTP request per matched language, and the
   translated-track request is the one YouTube rejects with a 429.
6. `YoutubeDL.py:4498-4501`: on a subtitle error, `if
   self.params.get('ignoreerrors') is not True: ... raise DownloadError(msg)`. Our
   effective `ignoreerrors` is the CLI default `'only_download'`
   (`options.py:386`), which `is not True`, so it raises.
7. `YoutubeDL.py:3392` (`_write_subtitles`) runs BEFORE the media download at
   `YoutubeDL.py:3536` (`self.dl(temp_filename, info_dict)`).

**Therefore the media file is never fetched at all.** This is not a transient
rate-limit; it is deterministic, which is exactly why Dean sees the same videos
fail on every retry: it depends on the video having translatable manual
subtitles, not on luck.

### Live verification against Dean's repro URL

An earlier draft of this section claimed our `en.*` regex explodes into ~130
requests. **That was wrong and is corrected here.** Running the real extraction
against `8Z2tmZy_Vj0` (yt-dlp 2026.07.04, `--list-subs --write-auto-subs`) shows
`en.*` matches exactly FOUR keys:

```
en          (automatic)
en-US       (manual)
en-en-US    (translated: the redundant one, and the one in Dean's 429)
en-orig     (automatic, original-language marker)
```

Re-running with `--extractor-args youtube:skip=translated_subs` yields exactly
`en`, `en-US`, `en-orig` - the offending `en-en-US` is gone and every genuine
track survives. So the defect is not request VOLUME, it is that we request one
redundant machine-translation track that YouTube rate-limits, and a failure on
that one redundant track takes the entire video download down with it.

The volume claim being wrong does not weaken the fix: layers L1 and L2 below are
both aimed at the verified mechanism (steps 6 and 7), not at request count.

### Verified landmine: `--extractor-args` REPLACES, it does not merge

`options.py:1927-1934` wires `--extractor-args` through
`_dict_from_options_callback` with `append=False`, so a second occurrence for the
same extractor key overwrites the first. Confirmed empirically against the real
parser:

```
--extractor-args youtube:player_client=android --extractor-args youtube:skip=translated_subs
  -> {'youtube': {'skip': ['translated_subs']}}                            # player_client DESTROYED

--extractor-args "youtube:skip=translated_subs;player_client=android"
  -> {'youtube': {'skip': [...], 'player_client': ['android']}}            # both survive
```

We already emit `--extractor-args youtube:player_client=<v>` when
`FILETUBE_YTDLP_PLAYER_CLIENT` is configured (`args.js:839`, the v1.31 bot-check
mitigation). Appending a second flag would therefore have SILENTLY disabled that
mitigation. Both settings must be emitted as one `;`-joined string.

### Fix: three layers

- **L1 (prevention).** Stop generating the request storm. Add
  `--extractor-args youtube:skip=translated_subs` (the precise switch checked at
  `_video.py:4224`) and narrow `--sub-langs` from the regex `en.*` to an explicit
  ordered set. Disclosed trade-off: a video whose only captions are translated
  FROM another language loses that fallback. Auto-generated English captions are
  unaffected.
- **L2 (containment).** Subtitle failure must never be able to abort a media
  download. On a subtitle-specific yt-dlp error, retry the item ONCE with the
  subtitle flags removed. The video always lands.
  - Explicitly rejected: blanket `-i/--ignore-errors`. Per `YoutubeDL.py:4499`
    it would fix this symptom, but it also downgrades genuine download and
    postprocessing failures to warnings ("the download will be considered
    successful even if the postprocessing fails"), which would make FileTube
    report broken downloads as successes. That trades a visible bug for an
    invisible one.
- **L3 (visibility).** Record the real reason in the item 7 failure log and mark
  the item `hasSubtitles: false`, so a caption-less download is legible rather
  than mysterious.

## Item 2 - Disable pinch-zoom (mobile)

Viewport meta alone is insufficient: iOS Safari has ignored `user-scalable=no`
since iOS 10. Requires suppressing `gesturestart`/`gesturechange`, applied
app-wide.

AS SHIPPED (gate SUGGESTION, adversarial seat - plan corrected to match
reality): this plan originally also listed "plus multi-touch `touchmove`". That
was deliberately NOT implemented. A non-passive `touchmove` handler that
preventDefaults on multi-touch would also eat two-finger scrolling, and it would
have to be non-passive on every touchmove in the app, which is exactly the
scroll-performance cost the v1.45.8 pull-to-refresh work went out of its way to
avoid. `gesturestart`/`gesturechange` already suppress pinch on WebKit, so the
extra handler bought nothing and risked a real regression. `gestureend` is also
deliberately unbound - preventing start+change is sufficient, and leaving end
alone keeps WebKit's own gesture bookkeeping intact.

`/read` (`public/read.html`, the EPUB/PDF reader) is carved out per Dean:
zoom is a genuine feature there, especially for PDFs. The carve-out must be by
explicit opt-out on that shell, not by a blocklist elsewhere, so a future shell
inherits the safe default.

Must NOT regress OS/browser text-size scaling (accessibility). Only gesture zoom.

## Item 3 - Pull-to-refresh indicator dies at finger-release

Confirmed by reading. `public/js/main.js:1188` `ptrEnd()` calls `runRescan()` and
then immediately `ptrReset()`, which strips the `visible` class. The scan runs on
with no indicator. The "Scanning..." affordance lives only on the Rescan button,
which is typically off-screen on mobile.

Fix: hand the indicator a "refreshing" state that the existing
`pollRescanStatus()` poller owns, cleared only when `scanning` flips false.
Reuse the existing poller; do not add a second one.

AS SHIPPED (gate SUGGESTION, QA seat - plan corrected to match reality): this
plan originally also specified "plus a short settle beat" before hiding. No
settle delay was implemented, deliberately: the indicator is cleared AFTER the
in-place grid refresh, and that ordering already prevents the stale-rows flash
the settle beat existed to avoid. A delay would only have kept a spinner up over
content that was already correct.

Must preserve the v1.45.8 gate CRITICAL: the `ptrIndicator.isConnected` guard
that keeps the whole pull path inert while Home is cached off-screen.

## Item 4 - Top-bar icons glitch/duplicate (NEEDS REPRO)

### What is provable today

`injectSubscriptionsNavLinkIfEnabled` (`public/js/common.js:1656`) has a real
idempotency hole, already partly logged as tech-debt #33(a):

- The guard is `document.querySelector('[data-nav="subscriptions"]')`.
- The BOTTOM-NAV link it creates gets `data-nav="subscriptions"` (line 1685).
- The SIDEBAR link it creates gets **no marker attribute at all** (lines
  1668-1676).

So on any shell without `#bottom-nav`, the guard can never become true and every
call appends another sidebar link. Separately, all four injectors check their
guard BEFORE an async `fetch` and never re-check after it resolves, so two
overlapping calls both pass and both inject.

### What is NOT proven

Those injectors run once at `DOMContentLoaded`, not per SPA swap, and the header
markup itself is static. So the provable bug does not yet explain a TOP-BAR
symptom appearing during in-app navigation. Icons are CSS `mask-image` over SVGs
(`style.css:3109+`), where a failed mask load renders as a solid filled box,
which is a plausible "glitches out" but not obviously a "duplicates".

**This item ships as two separate claims and the release notes must not blur
them:** (a) fixed a real idempotency defect, (b) Dean's symptom is fixed. Only
(a) is currently supportable.

Plan: fix the idempotency defects properly (marker attribute + post-fetch
re-check, not a de-dupe sweep), and add a singleton-invariant check behind
`?debugUI=1` that reports when an element expected to be unique has more than one
instance, so the next occurrence self-reports instead of being unpinnable.

**Open ask to Dean: a screenshot of the glitched top bar.** That converts this
from a hypothesis into a fix.

## Item 5 - Player touch input dies until force-quit (NEEDS REPRO)

Hypothesis class, from two precedents in this repo:

- **Touch-eating overlay.** The v1.17.0 T5 fix records exactly this failure:
  `.oneoff-modal-backdrop` had `display: flex` with no `[hidden]` override, so
  `hidden = true` left a full-viewport `z-index: 2100` overlay painted and eating
  every touch. Other fixed-position overlays need the same audit.
- **Latched gesture state.** `public/js/player.js:2754-2827`: `touchstart` arms
  `holdTimer`; `holdActive` is cleared only by `touchend`/`touchcancel`. The
  `touchend` handler returns early on `inNativeControlsMode()` BEFORE reaching
  its release path, and iOS does not reliably deliver `touchcancel` when a PWA is
  backgrounded mid-gesture. A latch that survives is consistent with "only a
  force-quit fixes it".

Plan: audit every `position: fixed` overlay for the `[hidden]`-override defect;
add lifecycle-driven defensive resets (`visibilitychange`/`pagehide` release the
hold latch and any armed gesture state); ship a `?debugTouch=1` instrument that
logs the topmost element at the touch point so a recurrence names its own culprit.

Same honesty split as item 4: defensive hardening is real work and worth
shipping, but it is not a proven fix for Dean's symptom until reproduced.

## Item 6 - PWA background survival (REFRAMED, agreed)

iOS exposes no cross-app isolation control. A backgrounded standalone PWA is a
WebKit process subject to jetsam, and closing another PWA can trigger the sweep
that reaps ours. "Never killed" is not deliverable and will not be claimed.

Acceptance, per Dean: **a kill costs nothing but the relaunch tap.**

Scope: continuously persist playback position, queue, and view state so relaunch
restores the exact spot; reduce resident footprint so we are a less attractive
jetsam target. Build on the existing v1.35 `audioSession`/pre-armed-sidecar work
rather than duplicating it.

## Item 7 - Unified download failure log

Today: `ytdlp-runs.jsonl` (`lib/ytdlp/runlog.js`) is durable, capped, atomically
written, and already fed by BOTH `runOneShot` and `processSubscription`
(`lib/ytdlp/index.js:3099, 3126, 3230, 2470, 285`), surfaced at
`GET /api/subscriptions/history`. What is missing is failure-level detail
(verbatim error text), and any way to clear it.

Build: a **Download Failures** view over the same durable store, with a source
column (one-off vs subscription) plus filter, the verbatim error string, a cap
(~200 entries), and BOTH clear-all and per-entry delete.

Reuse `runlog.js`'s existing atomic-write and defensive-read posture; do not
introduce a second persistence mechanism. Deletion is a data-losing operation on
a user-visible record, so per the repo norm it gets the FULL gate, never slim.

## Item 9 - Playlists sheet layout shift (SHIPPED)

Not a FOUC. A layout shift with two stacked causes:

1. **Serialized fetches.** The pins request was chained behind `/api/config`, so
   content arrived in two waves one network round-trip apart. The chaining had a
   real reason (`renderPlaylistsSheet` assigns `innerHTML` wholesale and would
   wipe an already-appended pinned section) but that is a RENDER-ORDER
   constraint, not a data dependency - the requests never needed to be
   sequential.
2. **The sheet is bottom-anchored**, so appending the pinned section grows it
   UPWARD. That is exactly Dean's "shifting everything up".

Fix: concurrent requests + one ordered render pass, so the sheet reaches its
final height in a single layout. Plus a last-payload cache painted
synchronously before any await, making every reopen shift-free. Cache is
paint-first only - every open still re-fetches, so a mid-session library change
still lands.

Three edge cases handled, each of which would otherwise reintroduce the shift:
superseded opens (generation guard), a failed config fetch (keep cached content
rather than replacing a good list with an error), and unpinning (update the
cache, or the next open paints the removed pin then drops it).
